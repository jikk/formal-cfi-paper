Figure~\ref{fig:system_overview} shows an overview of Picin\ae{}'s workflow.
Verifying a concrete binary entails first automatically \emph{lifting} it to a low-level, ISA-agnostic IL that explicitly encodes each instruction's machine-level effects.
Lifting can be accomplished with external tools or as Rocq code that produces IL from machine code bytes.
To support external lifters, we implement plugins for Ghidra~\cite{ghidra} and BAP~\cite{bap} that yield \Picinae{} IL from P-code and BIL code, respectively.
To support internal lifting, we implement instruction decoders for RISC-V and ARM7 in Gallina.

Internal lifting is critical for verifying a binary rewriter, since it allows proofs to reason about instruction encodings.
For example, a secure CFI implementation must not miss any control-flow transfer instructions in the target binary.
This can be proved by verifying that its instruction decoding logic correctly identifies and guards all opcodes whose ISA semantics perform control-flow transfers.

Lifting does not attempt perfect disassembly since it does not attempt to recover any control-flows from the binary.
It merely decodes the bytes at every virtual address, yielding a mapping from each address to each instruction's IL representation.
Recovering and verifying control-flows from this raw information is the province of proofs.
Formally verifying the lifting process is the subject of prior works~\cite{formally_verified_lifting,formally_verified_lifting_pic};
our focus in this work is on verifying properties of lifted codes, and properties of binary rewriters that produce code as bytes.

\Picinae{} IL's semantics formally define machine states $\sigma$ and \emph{traces} $\tau$ of machine states, facilitating theorems that express code safety, security, and functional correctness as properties of states and traces.
For example, theorems can assert that if $\tau=\sigma\ldots\sigma'$ is any reachable trace of the target program, and if $\sigma$ satisfies a specified pre-condition, then $\sigma'$ satisfies a specified post-condition.
Theorem specifications can span all operators in Rocq's calculus of inductive constructors (CiC), and proofs can leverage any of Rocq's proof-construction languages, such as Ltac\@.

To support the task of constructing proofs, \Picinae{} provides a rich theory of supporting theorems and proof tactic automation libraries.
This includes a fully machine-verified IL symbolic interpreter, binary arithmetic auto-simplification engine (for reducing expressions commonly arising from symbolic interpretation of binary code), inductive and co-inductive tactic libraries (for reasoning about loops and functions), temporal logic over traces, memory safety and pointer arithmetic theory, and architectural specializations of these for a variety of ISAs, including Intel x86/64, ARM7/8, and RISC-V.
All support libraries remain strictly untrusted; they are machine-verified by the Rocq core.

Inductive and co-inductive tactics facilitate a standard proof strategy that organizes unstructured control-flow paths through target binaries as inductive propositions.
Proofs declare \emph{invariants} (machine state properties) at function entry points, loop entry points, and join-points, from which \Picinae{} auto-generates proof goals that verify each invariant-bounded control-flow path (and prove that no other control-flow paths are reachable).
Solving all such goals creates a machine-checked proof that all realizable traces satisfy the theorem.
Co-induction affords partial correctness verification, and induction affords total correctness.

\Picinae{}'s IL models single-threaded, uninterrupted execution without superscalar or speculative execution;
however, it includes non-deterministic expressions to model unpredictable or implementation-defined cpu side-effects.
Non-deterministic expressions become universally quantified proof variables in proofs, requiring proofs to show that theorems hold irrespective of any non-deterministic decisions made by the microarchitecture, such as scheduling.

The proof script in Figure~\ref{fig:strcmp_proof} verifies that the machine state satisfies all declared invariants (including the postcondition) whenever they are reached, and no flows from the function entry point escape without first reaching the postcondition.
Line~\ref{l:proveinvs} begins by applying \Picinae's main co-induction theorem, splitting the partial correctness proof into a base case and an inductive case.
The base case is trivialized by locating the first invariant at the entry point (auto-solved by line~\ref{l:basecase}), so the remainder of the proof consists of verifying the flow from each non-postcondition invariant to the next.
Lines~\ref{l:inductivecase}--\ref{l:destructinv} set up these proof cases automatically.
The flow from entry point to loop invariant is verified by line~\ref{l:strcmp_entry_loop},
the flow for a loop iteration is verified by line~\ref{l:loopiteration},
and the two flows that exit the loop are verified by lines~\ref{l:exit1} and~\ref{l:exit2}.

Throughout the proof, \Picinae's \texttt{step} tactic performs verified symbolic interpretation of each machine instruction, inferring its effect upon the machine state, and its \texttt{psimpl} tactic performs verified auto-simplification of binary arithmetic expressions in the resulting symbolic state.
Both tactics auto-generate machine-checked proofs of their results, and Rocq's native linear integer arithmetic solver \texttt{lia} auto-solves generated goals.

\subsection{Verification Infrastructure}

Figures~\ref{fig:IL} and~\ref{fig:pil_semantics} show \Picinae{} IL's syntax and semantics, respectively.
Programs are functions that map a cpu state $\sigma$ and virtual address $a$ to an IL \emph{statement} $s$ that models the semantics of the machine instruction located at $a$ and its size $\mathit{sz}$ in bytes.
In von Neumann architectures, $p$ derives its output from the memory state in $\sigma$ by decoding the bytes at $a$ into an assembly instruction whose semantics are lifted to $s$.
This feature is critical for verifying a binary rewriter, since it makes the ISA's instruction decoding logic available to proofs.
Proofs may thereby verify that a rewriter's bit-manipulation logic correctly detects and/or generates ISA instructions with particular semantic properties.

Statements $s$ affect the cpu state $\sigma$ via no-operation ($\cdot$), destructive updates ($\coloneqq$) of machine state elements $v$ (e.g., registers and memory), jumps ($\mathtt{jmp}$), hardware exceptions ($\mathtt{exn}$), sequences ($;$), conditionals (${?}$), and finite repetitions ($s^e$).
Finite repetitions model individual instructions whose internal semantics contain a bounded micro-loop (e.g., the \texttt{rep} instruction prefix on Intel ISAs).
Expressions include state element reads ($v$), unsigned binary numbers $n$ of bit width $w$ ($n\ofwidth{w}$), $w$-byte reads of memory $e_1$ from address $e_2$ ($e_1[e_2]\ofwidth{w})$, $w$-byte memory-writes ($e_1[e_2\coloneqq e_3]\ofwidth{w}$), binary modular arithmetic operations ($\circledcirc$), bit width casts ($e:w$), let-bindings, and non-determinism ($*\ofwidth{w}$).
Non-determinism models side-effects that the ISA specifies are unpredictable or undefined.
For example, the Intel x86-64 ISA specifies that \texttt{xor} instructions have undefined effects upon the cpu's 1-bit arithmetic flag, which the lifter models as $\mathtt{AF}\:{\coloneqq}\:{*}\ofwidth{1}$.

Statements and expressions evaluate within an ISA \emph{context} $c$ that specifies the bit width of each cpu state element.
States may also include additional \emph{abstract} elements that are not part of a real cpu's state (e.g., for temporary values). %, a common practice in binary analyzers and disassemblers.
% Abstract elements have no bit width until they are assigned a value in a move statement.
Virtual memory of address width $w$ is modeled as a single state element of bit width $\twoto{.5}{\scriptstyle\twoto{.3}{\scriptscriptstyle w+3}}$.
A static semantics (not shown) ensures that each non-abstract assignment $v\coloneqq e$ preserves the ISA-defined bit width of $v$.
IL from external lifters is type-checked by a machine-verified type-checker, and internal lifters are machine-verified to be universally well-typed.
This relieves code verification proofs from re-proving fundamental properties of the ISA\@.
%This arrangement is designed to model the operational semantics of modern ISA lifter languages, such as Ghidra P-Code and BAP BIL, in a form expressible in Rocq.

Programs $p$ exhibit \emph{traces} $\tau$, which list cpu states paired with \emph{exits} $\chi$ (\textit{viz.}, the current virtual address $a$ or hardware exception number ${\uparrow}i$).
ISA function $\mathsf{exitof}$ defines the next virtual address reached by machine instructions that fall through (i.e., when $\chi={\fallthru}$).
The program-trace relation $p\leadsto\tau$ is non-deterministic:
For any given $p$, relation $p\leadsto\tau$ is satisfied by all traces $\tau$ that constitute valid execution sequences admitted by the ISA specification.
Partial correctness theorems therefore typically have the form $\forall\tau,(c\vdash p\leadsto\tau)\rightarrow P(\tau)$, which asserts that every trace $\tau$ realizable by program $p$ in ISA context $c$ satisfies proposition $P$.

Partial correctness proofs about concrete binary code are structured using \emph{invariant sets}---partial functions from virtual addresses to machine state properties.
Code verification is a co-induction with two cases:
(1) all traces through program $p$ satisfy the first invariant they reach (the base case), and
(2) every trace beginning at a satisfied invariant satisfies any next invariant it reaches.

Invariant sets automatically place fallacious invariants at all virtual addresses outside the target code fragment, guaranteeing that all such proofs provide full coverage (i.e., no reachable control-flow paths escape).

Formally, a program $p$ with exit points $\mathit{xp}\subset\mathbb{N}$
satisfies invariant set $\mathit{Invs}:a\rightharpoonup\Sigma\rightarrow\mathsf{Prop}$ if all realizable traces satisfy all reached invariants before exiting:
\begin{align}
&\mathit{NoExit}~\tau \coloneq \forall\langle a,\sigma\rangle\in\tau,~a\not\in\mathit{xp} \\
&\mathit{SatAll}~\tau \coloneq \forall a,\sigma,P,~(c\vdash p\leadsto\langle a,\sigma\rangle{::}\tau)\rightarrow\mathit{NoExit}~\tau\rightarrow(\mathit{Invs}~a=P)\rightarrow P(\sigma)
\end{align}
These definitions promote uniform theorem statements that assert standard assumptions about the initial machine state of trace $\tau$ (e.g., that it begins at the function entry point with a well-formed stack frame) and conclude $\mathit{SatAll}~\tau$.
Proofs make progress by leveraging antecedent $c\vdash p\leadsto\langle a,\sigma\rangle{::}\tau$ of $\mathit{SatAll}$ to infer that either (a) $a\in\mathrm{dom}(\mathit{Invs})$ is an invariant, which becomes the current proof goal; or (b) $a\not\in\mathrm{dom}(\mathit{Invs})$ must take at least one computational step before reaching any next invariant.

Picin\ae{}'s $\mathtt{step}$ tactic automates the latter case.
It launches a machine-verified symbolic interpreter that functionally infers the next symbolic machine state according to the IL semantics in Figure~\ref{fig:pil_semantics}.
This acts as an abstract machine code debugger that executes one machine instruction and generates a machine-checkable proof that its results are correct.
When the instruction is finite-branching, multiple next states are generated as multiple proof goals.
When it is non-deterministic or infinite-branching, the new states contain fresh, universally quantified proof variables that reflect all non-deterministic choices.
Proofs must therefore confirm that theorems hold for all possible branches and non-deterministic effects.
Invariant sets curtail state space explosion by coalescing all paths at invariant points to common invariant-defined proof goals.

One of the challenges faced with deductive verification of binary code is that expressions quickly grow too large to read and become cumbersome to manipulate.
Picin\ae{}'s simplifier \emph{psimpl} addresses this issue for expressions yielded by the symbolic interpreter, including store updates and reads, modular and bitwise arithmetic, and bit extraction.
%Psimpl is another reflexive tactic, it reduces expressions resulting from symbolic interpretation by turning the reduction into a computation with a certificate of correctness.
Psimpl is a reflexive tactic, effecting simplifications via computation certified with a proof of correctness.
The simplifier is a three-stage pipeline that overcomes both theoretical challenges of rewriting logics and the implementation idiosyncrasies of the Rocq proof assistant.
The first stage overcomes the computation engine's aggressive unfolding of definitions, even ones marked as opaque.
Psimpl first turns expressions into simplifier abstract syntax trees (SAST's), a deep embedding of Rocq's terms into a data structure whose semantics depend on a mapping from inductive symbols to the Rocq functions they signify.
This transforms the expression into one whose computation content is abstracted into a semantics, so $\mathsf{vm\_compute}$ only evaluates the function reducing the SAST, it never sees the computation functions it would reduce, such as $\mathsf{add}$ and $\mathsf{getmem}$.

% Greatly simplified treatment, does not cover the metavariables. More information on line 204 of the simplifier.v file.
The second stage simplifies the SAST using a postorder traversal.
The most important reduction is the elimination of modulo operations.
This depends on propogating upper and lower bounds of expressions during a traversal, simplifying modulo operations when the upper bound of the expression is less than the modulus.
Other simplifications include eliminating redundant update operations on stores, interpreting store lookups, and reducing arithmetic expressions, e.g., reducing $x+y-y'$ to $x$ when $y$ and $y'$ are provably equal.
After the simplifications the third stage transforms the SAST back into a Picin\ae{} expression.

Picin\ae{} facilitates modular reasoning about programs by supporting call-return semantics.
Once proved,the partial correctness proof of a callee can be applied inside of the proof of a caller to skip re-proving the callee providing sufficient conditions are met.
First, the callee invariants must imply any collocated caller invariants.
Second, the callee must not exit other than by reaching the return site, i.e., it must not raise a hardware exception or jump to a non-code address.
Third, the callee's invariants must be functions of the cpu state, i.e. they must be \emph{prefix-closed}~\cite{enforceable_security_policies}.
Picin\ae{} provides infrastructure for defining invariant sets and exits such that these conditions are guaranteed to be met for non-overlapping code fragments.

Picin\ae{} treats indirect calls and jumps like all other instructions.
Specifically, as a $\texttt{jmp}\ e$ statement, with $e$ a non-constant expression.

but the address being an expression rather than a constant complicates how the next instruction to execute is computed.
If the indirect call is to a function with an axiomatized partial correctness property, e.g., a function pointer to a comparator, then the function-call machinery can dispatch the function without the prover needing to define code in its section of memory.
In other cases the prover must specify what bytes are in memory or what that memory address decodes to.
This, in fact, is the basis for reasoning about binary transformations over arbitrary binary code.
