% inputs
The CFI rewriter is a function that takes the following inputs:
\begin{itemize}[topsep=0pt,itemsep=-1ex,partopsep=1ex,parsep=1ex, leftmargin=*]
\item \heading{Text Segment ($txt$):}
The rewriter is given the contents of the text segment of the program to rewrite, represented as a list of four-byte integers, the size of an ARM instruction.
\item \heading{Addresses ($bi, bi', tbi, ai$):}
The rewriter needs to know the addresses of various things\kjee{@Max what are various things here?} that we describe in more detail as they become relevant.
These addresses are passed to the rewriter as their value divided by four, for reasons also explained later.
\mxz{I',m not sure if I like deferring the explanation of these, but i don't know how else to structure this section}
When referring to values that represent addresses divided by four, we will use the term "index", as if memory was an array of four-byte values.
\item \heading{Policy ($pol$):}
The CFI policy describes what destinations each instruction of the text segment is allowed to go to.
Our rewriter accepts policies as a function from source indices to lists of permitted destination indices.
We do not impose any restriction on the destination sets; an index can belong to multiple distinct destination sets.
\end{itemize}

% block structure
The rewriter translates each instruction of the original text segment into one or more new instructions,
which we will refer to as a block (not to be confused with a basic block).
Thus, a block is a list of instruction encodings (list of ints) and the rewriter returns a list of blocks (list of lists of ints),
where the flattened list is the new text segment of the binary.

% index translation
We preserve the old text segment at its original location in the new binary, as we cannot distingush between code/data.
This, along with the fact that we insert additional instructions to enforce the policy,
means that blocks will be located at a different address than the original instruction that it corresponds to.
Therefore, the rewriter will need to translate between addresses in the original and new program.
For this, we use the $bi$ and $bi'$ inputs, which describe the index that the original text segment starts at (base index),
and the index where the rewritten text segment should be placed, and define a function $i2i'$ that performs this translation.

For rewritten programs to function correctly, it is sometimes necessary to allow instructions to jump to regions outside the new text segment.
As an example, on ARM the Linux kernel provides a couple of helper functions at fixed addresses that we cannot rewrite.
Therefore, $i2i'$ must return the input index when it does not fall within the original text segment range.
Otherwise, when $n$ is the $n$th index of the original text segment, $i2i'(n)$ is the index of the first instruction of the $n$th rewritten block.

% abort handler
When a rewritten program detects that an invalid control flow transfer would happen,
it instead goes to a user provided abort handler located at index $ai$.

% rewriting
The rewriter sequentially examines each original instruction and determines if it much be changed
to comply with the policy or to preserve functionality of the rewritten binary.
There are a few different cases we need to consider when rewriting an instruction.

\heading{Unchanged block.}
For most instructions, the rewriter does not have to make any changes as they are irrelevant to enforcing the policy.
The rewritten block contains the single unchanged instruction.

\heading{Non-control-flow change.}
In ARM, the program counter is allowed to be used as a register operand for some instructions.
Since the instruction's address has been changed by the rewriting process, the behavior of the rewritten program could be different.
Therefore, if the original instruction references the program counter register but does not perform any control flow,
the block first loads the original address of the instruction into a scratch register,
runs the original instruction with PC replaced with the scratch register,
and finally restores the scratch register to its original value.

Most ARM instructions use the first four bits of the encoding to allow conditional execution. A conditional instruction
should be rewritten into a conditional block.
Rather than propagating the condition field to each instruction of the block,
we choose to insert a branch at the beginning of the block with the
opposite condition that skips over the entire block to its immediate successor.
This choice allows us to make the rest of the block unconditional and not worry about cases where the flag bits change
in the middle of a block.

\heading{Direct control flow.}
If the instruction performs direct control flow, we check that its destination $d$ is permitted by the policy, and if so,
replace it with an instruction that branches to $i2i'(d)$. Otherwise, the instruction becomes a branch to $ai$.

\heading{Indirect control flow.}
If the instruction performs indirect control flow, we can only determine if the next step is policy permitted at runtime.
To perform this check, we devise a novel method using hash tables
that also allows us to easily translate addresses in the old text segment
to the corresponding address in the rewritten text segment.
For each indirect branch instruction, we insert code before to load a value from a table that only
contains permitted destination addresses and use that as the destination instead.
It is clear that such a block will always take permitted steps,
but care must be taken during table construction to ensure the original program behavior is preserved.

% hash table structure
Given a set of permitted destination indices $d = \{i_1, i_2, \dots\}$, we compute a table $t$ and hash function $H$ with the following properties:

\mxz{this looks ugly}

(1) $\forall i_j \in d, t\big[H(i_j)\big] = 4 \times i_j'$
(the program can compute the translated address of a valid destination by indexing into the table)

(2) $\forall i_j \in d, t\big[H(i_j')\big] = 4 \times i_j'$
(using a valid translated address to index the table gives back the same address)

% the previous two properties imply this one
% (3) $\forall i_j, i_k \in d, i_j \ne i_k \implies H(i_j) \ne H(i_k) \land H(i_j') \ne H(i_k') \land H(i_j') \ne H(i_k)$
% (there are no hash collisions, but we allow corresponding old and translated indices to have the same hash)

(3) $\forall n, \nexists i_j \in d, H(i_j) = n \implies t\big[n\big] = 4 \times ai$
(we fill unused slots in the table with the abort address)

For our implementation, we choose $H$ to be a function of the form $H(x) = \left\lfloor \frac{x}{2^{lsb}} \right\rfloor \bmod 2^w$ (bitsubstring),
which can be performed with a single instruction on ARM (\texttt{UBFX}, unsigned bit field extract),
and find appropriate parameters to minimize the size of the table for a given destination set while maintaining the listed properties.

Unlike other policy enforcement schemes that require destination sets to form equivalence classes such as in Abadi et al.,
using instruction-specific policy tables allows us to enforce policies where a destination can belong to any number of distinct sets.
Additionally, instructions that have the same destination set can share a table, minimizing space overhead.

As an example, consider the instruction \texttt{BX r0}, which branches to the address in \texttt{r0},
with an original destination set with indices \texttt{0x110}, \texttt{0x120}, and \texttt{0x130},
and a traslated destination set with indices \texttt{0x200}, \texttt{0x220}, and \texttt{0x240}.
The optimal parameters for $H$ are $lsb=4$ and $w=3$, extracting bits 4 to 6 from each index.

    \heading{Endianness.}
    ARM supports both little and big endian memory operations, determined by the value of the E bit of the Current Program Status Register.
    While it does not matter which endianness we start in as long as the hash tables are also in the same endianness,
    changing the E bit at runtime could allow unpermitted control flow since instructions loading destination addresses from the hash tables will load different values.
    Support for this feature could be added by setting the E bit in each dynamic control flow block and restoring the previous value after loading the table,
    but we instead choose to omit support as it is not commonly used.

    \heading{Instruction mode.}
    ARMv7 provides four different instruction states determined by the J and T bits of the CPSR: ARM, Thumb, Jazelle, and ThumbEE.
    We only consider the ARM instruction set and do not support any of the other modes.
    While we can remove some instructions that will always change the instruction state,
    there are certain instructions that that we need to use that could still change the instruction state.
    Most notably, dynamic control flow instructions will change the instruction state to Thumb mode when the least significant bit of the destination address is 1.
    For this reason, we describe all addresses as indices, so no entry of the hash table will switch the instruction state.
    We omit the support for these additional instruction modes because Jazelle and ThumbEE are extremely niche, and
    support for Thumb mainly just requires duplicating work to accommodate the different instruction encodings.

    \heading{\unpredictable{} instructions.}
    Certain instructions are defined to be \unpredictable{}. The manual describes this term as:
    \begin{displayquote}
        Means the behavior cannot be relied upon. \unpredictable{} behavior must not perform any function that cannot be performed at the current or a lower level of privilege using instructions that are not \unpredictable{}.
    \end{displayquote}
    Although in practice, these instructions usually just cause a hardware exception \mxz{maybe?}, this definition includes the possibility of performing unpermitted control flow.
    Thus, the rewriter must detect and remove all such instructions. Most instruction types include at least a few \unpredictable{} variants, either from use of the PC register for instructions that do not support it or from the instruction encoding requiring certain bits to be 0 or 1. A couple of instructions are only \unpredictable{} at runtime, including dynamic control flow instructions when the destination address ends with the bits '10'. This issue is avoided the same way we prevent switching to Thumb mode, by enforcing that all hash table entries are divisible by four.
    }

% python/ocaml extractor
The ELF editor is given the output of the CFI rewriter and adds new segments to the original ELF for the rewritten instructions, the policy tables, and the abort handler that are loaded at the correct addresses and permissions. The original text segment is changed to be nonexecutable. Finally, the ELF editor uses the rewriter's $i2i'$ function to update the entrypoint and symbol values.

\subsection{Workflow \ixb{Tentative title}}
As we would like to formally verify the soundness of our CFI implementation,
we implement the CFI rewriter as a function in Gallina,
the specification language of Rocq, to allow us to write machine-checked proofs about its behavior.
The rewriter function is extracted into OCaml and compiled into an executable
with some additional driver code for reading/writing files and argument parsing.
The ELF editor is implemented as a Python script using the LIEF library.
We do not formally verify the correctness of the extraction process
the additional OCaml code, or the ELF editor,
instead only focusing on the core rewriting logic that transforms the instruction bytes,
as verification of the other components is not particularly interesting or
has been covered by previous works in the case of verified extraction.

However, we are still left with a difficult problem.
To prove the soundness of the rewriter,
we must prove that every execution through every binary that the rewriter outputs
complies with the provided policy.
Even ignoring ... \mxz{something something state explosion for every trace},
existing frameworks for bottom-up verification are incapable of proving properties
of binary code that is not completely concrete,
preventing us from proving anything about code where the only known information is that
it was produced by some input to the rewriter.
