\subsection{Rewriter Design}\label{sec:cfi_design}

Figure~\ref{fig:cfi_arch} depicts the design of \pname, consisting of two main components:
(1) the CFI rewriter, which transforms a list of instructions into a rewritten, CFI-instrumented list of instructions;
and (2) the \ELFPackager, which packages the new instruction list into an ELF file.
The former is implemented in Rocq and its soundness is verified in \S\ref{sec:verification}.
The verified Rocq code is extracted to OCaml, linked with minimal wrapper code for file IO, and compiled into the executable that performs the binary rewriting.
The \ELFPackager is a Python script that packages the rewritten code into an ELF file.

The CFI rewriter is a Rocq function with the following inputs:
\begin{itemize}[topsep=1ex,itemsep=-1ex,partopsep=1ex,parsep=1ex, leftmargin=*]
\item \heading{Text Segment ($\ell$):}
The rewriter receives the contents of the text segment of the original program as a list $\ell$ of 4-byte integers.
\item \heading{Addresses ($\bi, \bip, \tbi, \mai$):}
The rewriter also receives the locations of the original and new code sections (\bi{} and \bip, resp.), the address-translation table (\tbi), and the safe abort code (\mai).
Each location is the index $i$ of a 4-byte virtual memory address~$4i$.

% When referring to values that represent addresses divided by four, we will use the term "index", as if memory was an array of four-byte values.
\item \heading{Policy (\pol):}
The CFI policy specifies the set of permitted destinations of each instruction in the text segment.
It is expressed as a function from source indices to lists of permitted destination indices.
Policies may specify arbitrary destination sets, including non-disjoint, non-identical sets for different instructions.
\end{itemize}

% block structure
The rewriter translates each instruction of the original text segment into a \emph{\Block} of one or more new instructions.
Thus, a \Block is a list of instruction encodings (list of ints) and the rewriter returns a list $\ell'$ of \Blocks (\ie a list of lists).
Flattening list $\ell'$ yields the rewritten text segment of the output binary.

% index translation
We preserve the old text segment as a non-executable data section at its original location in the new binary to preserve static data.
All executable code is therefore relocated during rewriting.
The rewriter implements a function \itoip that maps each original instruction location to its rewritten \Block location, defined by
\begin{equation}\label{eq:itoip}
\itoip(\bi+j) = \begin{cases} \bip+\sum_{k=1}^{j-1} \left|\ell'[k]\right| & \text{if $j\in[0,|\ell|)$} \\
                              \bi+j & \text{otherwise} \end{cases}
\end{equation}
where $\ell'[k]$ is the $k$th \Block in output list $\ell'$

Rewritten code must sometimes jump to regions outside its new text segment.
For example, the ARM Linux kernel provides helper functions that cannot be relocated to fixed addresses.
Therefore, \itoip returns the input index when it does not fall within the original text segment range.
Otherwise, $4\itoip(\bi+j)$ is the address of the first instruction of the $j$th rewritten \Block.

% abort handler
%When a rewritten program detects an impending invalid control-flow transfer, it redirects control to the safe abort handler located at index $\mai$.

% rewriting
The rewriter sequentially examines each original instruction and determines whether it must be changed
to comply with the policy or to preserve functionality:

\heading{Unchanged instructions.}
Most instructions are irrelevant to enforcing the policy, and are therefore rewritten to single-instruction \Blocks that preserve the original instruction.

\heading{Non-control-flow change.}
Some ARM instructions accept the \PC as a register operand, causing their behavior to change when relocated.
If the original instruction references the \PC without transferring control,
the rewritten \Block code first loads the original address of the instruction into a scratch register,
runs the original instruction with PC replaced with the scratch register,
and finally restores the scratch register to its original value.

Most ARM instruction encodings use the first four bits as a conditional execution prefix.
A conditional instruction must be rewritten to a conditional \Block.
Rather than propagating the condition field to each instruction of the \Block,
we start the \Block with an opposite-condition branch to the succeeding \Block.
This avoids difficulties where the flag bits can change within the \Block.

\heading{Direct control flow.}
If the instruction performs direct control flow, we replace it with an instruction that branches to $\itoip(d)$ if its destination $d$ is policy-permitted, and to $\mai$ otherwise.

\heading{Indirect control flow.}
If the instruction performs an indirect control-flow transfer, it becomes guarded by a runtime security check.
To perform this check with minimal branching, we devise a novel method using hash tables
that translate addresses in the old text segment to corresponding addresses in the rewritten text segment.
The translation code uses the old destination as a lookup key for a hash table that consists exclusively of permitted destination addresses for that instruction.
Soundness verification of the guard code therefore reduces to proving table integrity.
%Care must be taken during table construction to ensure the original program behavior is preserved.

% hash table structure
Given a set of permitted destination addresses $D = \{a_1, a_2, \dots\}$, a suitable table $T_D$ and hash function $h$ must satisfy the following:
\begin{enumerate}
\item \textbf{Completeness:} $\forall a \in D, T_D[h(a)] = 4\itoip(a/4)$
% (the program can compute the translated address of a valid destination by indexing into the table)
\item \textbf{Idempotency:} $\forall a \in D, T_D[h(4\itoip(a/4))] = 4\itoip(a/4)$
% (using a valid translated address to index the table gives back the same address)
%
% the previous two properties imply this one
% (3) $\forall i_j, i_k \in d, i_j \ne i_k \implies H(i_j) \ne H(i_k) \land H(i_j') \ne H(i_k') \land H(i_j') \ne H(i_k)$
% (there are no hash collisions, but we allow corresponding old and translated indices to have the same hash)
\item \textbf{Safety:} $\forall n\not\in h|_D, T_D[n] = 4\mai$
% (we fill unused slots in the table with the abort address)
\end{enumerate}
Completeness ensures that each permitted jump target is redirected to the correct rewritten \Block target.
Idempotency ensures that permitted, already-redirected targets (\eg addresses drawn from the \PC of the rewritten code at runtime) are preserved.
Safety ensures that all impermissible jumps are aborted.

To statically generate a minimal-sized table $T_D$ for an instruction with destination set $D$, our implementation iteratively populates candidate tables of increasing size, discarding those that violate completeness, idempotency, or safety, until it finds a table with no property-violating hash collisions.
If the resulting table equals that of another rewritten instruction, the duplicate table is discarded and both instructions share a table.
This is a common case since most policies constrain many instructions similarly (\eg by grouping method calls into equivalence classes by type signature~\cite{tau_cfi}).

To implement hash function $h$ efficiently, we choose bit-substring function $h(x) = ({x}\gg\mathit{lsb}) \bmod 2^w$,
which can be performed with a single instruction on ARM (\texttt{UBFX}, unsigned bit field extract).
Parameters $\mathit{lsb},w\in[0,32)$ are chosen to minimize table size $|T_D|$.

Unlike prior enforcement strategies that require destination sets to form equivalence classes, such as those that in-line unique labels at destination addresses~\cite{abadi_cfi},
using instruction-specific policy tables allows us to enforce policies where a destination can belong to any number of distinct sets.
It also reduces the number of conditional instructions added to rewritten code, reducing the space of control-flow paths that must be considered during verification.

    \heading{Endianness.}
    ARM supports both little and big endian memory operations, determined by the value of the E bit of the \CPSR.
    Changing the E bit at runtime could risk policy violations by loading addresses from policy tables in a different byte order than they were stored.
    \pname therefore replaces endianness mode-switching instructions with safe aborts.
    Future work could support mixed endianness by setting and restoring the E bit before and after table-reads.

    \heading{Instruction mode.}
    ARMv7 provides four different instruction states determined by the J and T bits of the \CPSR: ARM, Thumb, Jazelle, and ThumbEE.
    For this work we focus exclusively on ARM mode.
    Jazelle and ThumbEE are rare in practice, and Thumb support is reserved as a future extension that can be accommodated with more instruction encodings.
    To disallow the other modes, \pname detects and removes mode-changing instructions, and disallows indirect control-flow transfers to odd-valued destination addresses, since such jumps change the instruction state to Thumb mode.
    The latter is achieved by storing only even-valued addresses in tables~$T_D$.

Most instruction types include at least a few \unpredictable{} variants, such as from unsafe uses of \PC register operands or invalid instruction encodings. Once the CFI rewriter has generated a new code section, the \ELFPackager adds new segments to the original ELF for the rewritten instructions, the policy tables, and the abort handler with correct base addresses and permissions. The original text segment is changed to be non-executable. Finally, the entry point and symbol values are updated using the rewriter's \itoip function.

Although mainstream \FM frameworks such as Rocq and Isabelle/\penalty0 HOL have built-in support for machine-proving properties of concrete codes implemented in their respective specification languages, they do not natively support verifying properties of codes expressed in other languages or produced by other tools.
Therefore, although implementing our rewriter as a Gallina function affords Rocq the capacity to directly reason about its implementation, it does not afford the capability of proving properties of the machine code that it outputs.

This presents a difficult \FM challenge:
The rewriter soundness property we must verify is a universally quantified property of all possible executions on all possible ISA-compliant computational environments of all possible machine code programs that the rewriter might generate.
To address this challenge, we turn to the \Picinae{} framework, described in the next section.
