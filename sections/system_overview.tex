\subsection{Rewriter Design}\label{sec:cfi_design}

Figure~\ref{fig:cfi_arch} depicts the design of \pname, consisting of two main components:
(1) the CFI rewriter, which transforms a list of instructions into a rewritten, CFI-instrumented list of instructions;
and (2) the ELF editor, which packages the new instruction list into an ELF file.
The former is implemented in Rocq and its soundness is verified in \S\ref{sec:verification}.
The verified Rocq code is extracted to OCaml, linked with minimal wrapper code for file IO, and compiled into the executable that performs the binary rewriting.
The ELF editor is a python script that packages the rewritten code into an ELF file.

The rest of this section details the design of the CFI rewriter, which is expressed in Rocq as a function from the following inputs:
\begin{itemize}[topsep=0pt,itemsep=-1ex,partopsep=1ex,parsep=1ex, leftmargin=*]
\item \heading{Text Segment ($\ell$):}
The rewriter receives the contents of the text segment of the original program as a list $\ell$ of 4-byte integers.
\item \heading{Addresses ($\bi, \bip, \tbi, \mai$):}
The rewriter also receives the locations of the original and new code sections (\bi{} and \bip, resp.), the address-translation table (\tbi), and the safe abort code (\mai).
Locations (\bi, \bip, etc.) are indexes of each 4-byte address in virtual memory, which equals its virtual address divided by 4.

% When referring to values that represent addresses divided by four, we will use the term "index", as if memory was an array of four-byte values.
\item \heading{Policy (\pol):}
The CFI policy specifies the set of permitted destinations of each instruction in the text segment.
Our rewriter accepts policies as a function from source indices to lists of permitted destination indices.
Policies may specifiy arbitrary destination sets; non-disjoint sets are supported.
\end{itemize}

% block structure
The rewriter translates each instruction of the original text segment into a \emph{\Block} of one or more new instructions.
Thus, a \Block is a list of instruction encodings (list of ints) and the rewriter returns a list of \Blocks (\ie a list of lists).
The flattened list is the rewritten text segment of the output binary.

% index translation
We preserve the old text segment as a non-executable data section at its original location in the new binary to preserve static data.
All executable code is therefore relocated during rewriting.
The rewriter implements a function \itoip that maps each original instruction address to its rewritten \Block address using their respective base addresses ($\bi$ and $\bip$).

Rewritten code must sometimes jump to regions outside its new text segment.
For example, the ARM Linux kernel provides helper functions that cannot be relocated to fixed addresses.
Therefore, \itoip returns the input index when it does not fall within the original text segment range.
Otherwise, $\itoip(4n)$ is the address of the first instruction of the $n$th rewritten \Block.

% abort handler
When a rewritten program detects an impending invalid control-flow transfer,
it redirects control to the safe abort handler located at index $\mai$.

% rewriting
The rewriter sequentially examines each original instruction and determines whether it must be changed
to comply with the policy or to preserve functionality:

\heading{Unchanged instructions.}
Most instructions are irrelevant to enforcing the policy, and are therefore rewritten to single-instruction \Blocks that preserve the original instruction.

\heading{Non-control-flow change.}
Some ARM instructions accept the program counter as a register operand, causing their behavior to change when the instruction is relocated.
If the original instruction references the program counter without transferring control,
the rewritten \Block code first loads the original address of the instruction into a scratch register,
runs the original instruction with PC replaced with the scratch register,
and finally restores the scratch register to its original value.

Most ARM instructions use the first four bits of the encoding for conditional execution.
A conditional instruction should be rewritten into a conditional \Block.
Rather than propagating the condition field to each instruction of the \Block,
we insert a branch with opposite condition at the start of the \Block, which skips to the \Block's immediate successor.
This avoids difficulties where the flag bits change within the \Block.

\heading{Direct control flow.}
If the instruction performs direct control flow, we replace it with an instruction that branches to $\itoip(d)$ if its destination $d$ is policy-permitted, and to $\mai$ otherwise.

\heading{Indirect control flow.}
If the instruction performs an indirect control-flow transfer, it becomes guarded by a runtime security check.
To perform this check with minimal branching, we devise a novel method using hash tables
that translate addresses in the old text segment to corresponding addresses in the rewritten text segment.
The translation code uses the old destination as a lookup key for a hash table that consists exclusively of permitted destination addresses for that instruction.
Soundness verification of the guard code therefore reduces to proving soundness of the table contents.

    \heading{Endianness.}
    ARM supports both little and big endian memory operations, determined by the value of the E bit of the Current Program Status Register.
    Changing the E bit at runtime could risk policy violations by loading destination addresses from hash tables in a different byte order than they were stored.
    \pname therefore replaces endianness mode-switching instructions with safe aborts.
    Support for mixed endianness could be added by setting the E bit in each dynamic control flow block and restoring its previous value after table-read is complete.

    \heading{Instruction mode.}
    ARMv7 provides four different instruction states determined by the J and T bits of the CPSR: ARM, Thumb, Jazelle, and ThumbEE.
    For this work we focus exclusively on ARM mode.
    Jazelle and ThumbEE are rare in practice, and Thumb support is reserved as a future extension that can be accommodated with more instruction encodings.
    To disallow the other modes, \pname detects and removes mode-changing instructions, and disallows dynamic control-flow transfers to odd-valued destination addresses, since they change the instruction state to Thumb mode.
    The latter is achieved by implementing all destination addresses as indices, so no hash table entries are odd.

    \heading{\unpredictable{} instructions.}
    Certain instructions are defined to be \unpredictable{}. The manual describes this term as:
    \begin{displayquote}
        Means the behavior cannot be relied upon. \unpredictable{} behavior must not perform any function that cannot be performed at the current or a lower level of privilege using instructions that are not \unpredictable{}.
    \end{displayquote}
    Although in practice, these instructions usually just cause a hardware exception \mxz{maybe?}, this definition includes the possibility of performing unpermitted control flow.
    Thus, the rewriter must detect and remove all such instructions to guarantee safety for arbitrary ISA-conformant cpus. Most instruction types include at least a few \unpredictable{} variants, either from use of the PC register for instructions that do not support it or from the instruction encoding requiring certain bits to be 0 or 1. A couple of instructions are only \unpredictable{} at runtime, including dynamic control flow instructions when the destination address ends with the bits '10'. This issue is avoided the same way we prevent switching to Thumb mode, by enforcing that all hash table entries are divisible by four.

The ELF editor is given the output of the CFI rewriter and adds new segments to the original ELF for the rewritten instructions, the policy tables, and the abort handler that are loaded at the correct addresses and permissions. The original text segment is changed to be nonexecutable. Finally, the ELF editor uses the rewriter's \itoip function to update the entrypoint and symbol values.

With formal verification, the price of high assurance is the labor of proving.
Can cut some of the costs by using FM-friendly design principles

\heading{Minimize conditionals.}
Each conditional doubles the number of traces we must consider; we must reason about the case when the condition is true and false.
In our design, we enforce the policy without using conditionals, as each indirect jump becomes a conditionless policy table lookup.
We do not need to separately prove correct policy enforcement when the destination is permitted or prohibited,
since in both cases the destination becomes a value from the table, which only contains permitted destinations.

\heading{Code reuse.}
Reusing code means we can reuse proofs about the code.
We use the same sequence of instructions to load from a policy table in every indirect branch block,
allowing us to only have to prove the code always results in a state with a permitted destination once.

\heading{Global state independence.}
Some policy enforcement strategies require a property of the entire code space to be true.
For example, the soundness of label-based approaches relies on the labels chosen not appearing anywhere
in executable memory other than valid destinations.
On the other hand, our table-based approach only requires us to consider the current block being executed and its corresponding policy table.
It is a lot easier to reason about a single block at a time rather than the entire program.
Additionally, in some cases we do not even know all of the executable code in memory
(such as the kernel-provided code mentioned above).

\heading{Minimize preconditions.}
For every precondition needed for correctness, we must prove that it always holds when necessary.
We can counter this by designing our code in a way that minimizes the necessary preconditions or makes proving them easy.
As an example, before using a hash to perform a table lookup, it is necessary that the hash is less than the length of the table
or else the value loaded will not be from the table.
However, this is the only precondition we depend on;
we do not need to prove any other property of our hash function
such as uniformity or collision resilience.

We need the stack pointer to be word-aligned in some cases
(we explain later in \autoref{sec:case_studies} why this is necessary).
One way to enforce this would be to detect all instructions that could cause
\texttt{SP} to become unaligned and realign it afterwards,
while ignoring changes to \texttt{SP} that leave alignment intact.
Instead, we choose to just always realign \texttt{SP} right before it is needed,
making the proof significantly easier.

\heading{Immutable security state.}
Allowing security relevant state to change makes the proof much more difficult,
as it both increases the number of possible states and requires us to prove that the state never becomes invalid.
In our design, the rewritten code and policy tables are both non-writable, so we do not have to deal with this.

\heading{Nondeterminism independence.}
Relying on the results of non-deterministic cpu operations, \eg XOR setting ZF to a random bit in x86, runs the risk of requiring the proof to reason about the execution of symbolic instructions at a granularity that is not readily supported.
While feasible, this requires a careful sequence of destructs and inversion rules.
For example, to prove semantic transparency one must show that a cpu state in a transformed program is reachable by the original program.
For deterministic programs, this is easy.
With the addition of non-determinism you must prove the non-deterministic operation could take a branch satisfying the state similarity property.

\heading{Stack independence.}
Using the stack introduces the obligation of proving the rewriter is correct despite changes to memory.
We use the stack anyways, because our immutable security state makes safety-violating memory changes trivially unreachable.
Any rewriter whose correctness relies on a predictable \emph{mutable} memory region should minimize spurious memory modifications.

\heading{Inductive proof structure.}
Breaking the proof into invariant points and applying inductive reasoning is a well known way of simplifying program verification to its necessary subcomponents.
\Picinae{} offers facilities for doing this that work just as well on symbolic code as they do on concrete.
