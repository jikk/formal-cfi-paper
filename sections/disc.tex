\section{Discussion and Future Work}\label{sec:disc}
{% optional.
    This section situates \pname within the broader goal of end-to-end verified binary rewriting. We first delineate the current verification boundary and the trusted assumptions that underlie our guarantees. We then discuss how the approach extends beyond stateless CFI to richer classes of in-lined reference monitors, highlighting new challenges in protecting monitor state. Finally, we outline the generality of our methodology across ISAs and its applicability to a broader class of binary rewriting systems.
}

\subsection{Verification Scope and Trusted Assumptions}\label{sec:elf_packager_fm}

\pname provides high assurance by formally verifying the binary rewriter under a small set of trusted components and modeling assumptions.
%
At the front end, we do not verify the decoder and lifter. The lifter implements ARMv7 ISA semantics in Gallina and translates binary instructions into \Picinae \IL statements. We treat it as trusted, but two factors reduce the risk: ARMv7 has an existing formal specification, and prior work has extensively explored verified and semi-verified decoding and lifting pipelines, indicating a path toward full verification (see \autoref{sec:fm_related}).

Building trustworthy mechanized ISA semantics remains challenging. Although Rocq verifies extraction to OCaml, we introduce a performance-driven refinement by mapping unbounded integers ($Z$) to bounded machine integers ($int$). Rocq supports proving this refinement sound, but we leave that proof for future work.

We also trust the ELF packaging stage. Its correctness depends on the program loader, which lies outside our model. Verifying this stage therefore requires reasoning about binary loading, making end-to-end guarantees an open problem.

\Picinae{}'s ISA model further abstracts away concurrency, shared memory, and system calls. As a result, our guarantees apply only to isolated execution and do not cover OS-level attacks such as sigreturn-oriented programming. The current design also assumes a single contiguous code section.

Extending verification to the full rewriting pipeline remains future work. A promising direction is *program loader verification*, which seeks to formally specify and verify binary loading semantics, though it introduces substantial challenges.

Finally, our formalization focuses on the \cd{.text} section and treats other binary components, including ELF metadata, relocations, and dynamic linking structures, as trusted. Extending guarantees to these components is a natural next step toward fully verified binary rewriting.

    \subsection{Formal Verification of \ELFPackager}\label{sec:elf_packager_fm}
    Although \pname{} is, to our knowledge, the first formally verified binary CFI rewriter, its guarantees do not yet extend to the entire binary rewriting pipeline. In particular, the ELF packaging component lies outside the scope of the current formal model. Extending formal verification to this stage presents nontrivial challenges and can be approached along two possible directions.

    One approach is \emph{supply-chain verification}, which would require formally verifying the existing Python implementation or reimplementing the ELF manipulation logic (e.g., the LIEF library) within a proof assistant such as Rocq. However, this direction is likely impractical due to the substantial engineering effort required to formalize and maintain large, general-purpose codebases. A second, more ambitious direction is \emph{program loader verification}, which aims to formally verify the correctness of the binary loading process against a well-defined security specification. This approach would provide stronger end-to-end guarantees but remains a challenging open research problem.

    More broadly, our current formalization focuses on the \texttt{.text} section, the executable instruction stream, and treats other components of the binary, including ELF metadata, relocation entries, and dynamic linking structures, as trusted. Extending formal guarantees to cover the full pipeline, including ELF packaging and loading, remains an important direction for future work.
}

\subsection{Secure In-lined Reference Monitors (IRMs)}
\kjee{Here we want to mention another aspect that the effort needs to go by hand-in-hand binary security and FMs. Generalization via framework building can be very ambitious but highly rewarding next research milestone.}
Extending our approach to formally verify broader classes of secure IRMs is a natural and meaningful next step. IRMs transform an untrusted binary into a hardened version by embedding security checks directly into the code. This transformation partitions execution into two contexts: the guest context, which runs the original program, and the monitor context, which enforces the security policy.

IRMs differ in their degree of statefulness. Static binary CFI, as implemented in \pname, is a stateless IRM: the control-flow policy remains fixed and requires no persistent monitor state. In contrast, stateful IRMs maintain evolving security state, such as shadow memory for information flow tracking or allocation histories for memory safety policies.

Regardless of statefulness, protecting the monitor context from interference by the untrusted guest context remains a central challenge. Both contexts execute at the same privilege level, and enforcing isolation must avoid prohibitive overhead. While this issue lies outside the stateless CFI setting considered in this work, it presents a compelling direction for future research in formally verified binary rewriting.

\subsection{Cross-ISA Generalization and Applicability}
Our verification approach generalizes to other architectures supported by \Picinae{}. For each ISA, an internal lifter implemented in Gallina decodes instructions and translates them into \pil\@. Given such a lifter, one can construct proofs analogous to those in this work to establish comparable security guarantees.

More broadly, our verification methodology and the design principles outlined in \autoref{sec:fm_friendly} extend beyond CFI to other binary rewriting applications, including emulators, dynamic patchers, and profilers. These principles help reduce verification complexity but do not impose strict constraints on system design.

For example, \pname is not fully stack-independent, as it uses the stack to save registers. Similarly, rewriters that maintain mutable security state remain verifiable in principle, but they introduce additional proof obligations and typically require greater verification effort.
