In order to provide a high-assurance binary defense by formally verifying the binary rewriter, \pname{} trusts other components of the system.
Underlying the rewriter is the internal lifter, a manual implementation of the ARMv7 ISA semantics as a Gallina function translating code bytes to PIL statements.
Creating trustworthy mechanized semantics of ISAs is a subject of ongoing research~\cite{isla,islaris,archsem,armstrong19isasem,liblisa,goel17x86isa}.
While extraction from Rocq to OCaml is verified~\cite{fv_ocaml_extraction}, the extracted code makes one undermining translation to make the rewriter run faster.
It translates Rocq's unbounded integer type \texttt{Z} to OCaml's bounded machine integers \texttt{int}.
Rocq offers facilities for proving the soundness of this extraction choice, but we leave it as future work.
The ELF Packager is trusted, but its verification relies on the behavior of the loader that loads the binary and as such requires a formally verified loader.
Creating such a component is an open problem, thus verifying the ELF Packager is out of scope.

Besides the trusted components, our ISA semantics model does not account for concurrent execution, shared memory, nor system calls.
Thus, the security guarantees of our rewriter are restricted to programs executed in isolation without interacting with the OS.
Systems that do call out to the OS, for instance, are vulnerable to sigreturn-oriented programming attacks.
Its architecture also limits it to a single contiguous code section.

\subsection{Generalizability}

Our verification approach generalizes to all other architectures supported by \Picinae{}.
% , but requires an up front investment. % first sentence of the section shouldn't be a negative
An internal lifter written in Gallina decodes ISA instructions and returns their representation in PIL.
% Each architecture requires an internal lifter that formalizes its instruction-decoding in Gallina and instruction semantics in PIL.
Given an internal lifter, similar proofs to those discussed in this work are constructed to provide similar security guarantees.

The formal verification approach and the design principles outlined in~\autoref{sec:fm_friendly} generalizes to other binary rewriting applications,
\eg emulators, dynamic patchers, and profilers.
In each case our design principles help reduce the formal verification burden, but do not act as constraints.
For example, \pname{} is not stack independent because it uses the stack to save registers.
Rewriters that introduce mutable security state are verifiable in principle, but likely to require more human effort.

\subsection{Formal Verification of ELF Packager}\label{sec:elf_packager_fm}
\kjee{Tentative text; need refinement and text tightening.}

Although \pname{} is, to our knowledge, the first formally verified binary CFI rewriter, its guarantees do not yet extend to the entire binary rewriting pipeline. In particular, the ELF packaging component lies outside the scope of the current formal model. Extending formal verification to this stage presents nontrivial challenges and can be approached along two possible directions.

One approach is \emph{supply-chain verification}, which would require formally verifying the existing Python implementation or reimplementing the ELF manipulation logic (e.g., the LIEF library) within a proof assistant such as Rocq. However, this direction is likely impractical due to the substantial engineering effort required to formalize and maintain large, general-purpose codebases. A second, more ambitious direction is \emph{program loader verification}, which aims to formally verify the correctness of the binary loading process against a well-defined security specification. This approach would provide stronger end-to-end guarantees but remains a challenging open research problem.

More broadly, our current formalization focuses on the \texttt{.text} section, the executable instruction stream, and treats other components of the binary, including ELF metadata, relocation entries, and dynamic linking structures, as trusted. Extending formal guarantees to cover the full pipeline, including ELF packaging and loading, remains an important direction for future work.

    \pname{}'s formal guarantees cover only a portion of the system.
    First, the proof assumes, and thus integrity holds, only if the old text section, new text section, policy tables, and abort are all situated in memory in their proper positions and execution begins at the beginning of a block.
    The rest of the \pname{} and ELF pipelines between rewriting and execution is not verified.
    This includes the OCaml ELF parser, the Python ELF Packager from \pname{}, and the system's ELF loader.

    Verifying the entire pipeline would be a tremendous work, involving 3 languages, a file format without a formal specification, and an OS component that has hereto evaded the inspection of the FM community.
