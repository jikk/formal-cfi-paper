\section{Formal Verification of CFI Binary Rewriter}
\label{sec:back}

\pname formally verifies a program transformation: a static binary rewriter that takes arbitrary binaries as input and produces security-hardened outputs guaranteed to satisfy a precise safety specification.
The precise specification is universal to all binary code for the ISA; once written, it never needs to be specialized to a new rewriter.

Formal reasoning about static binary rewriting (or binary-to-binary transformations) presents fundamental challenges. The input space is vast and highly irregular, lacking the structural guarantees available at the source level. Verification requires precise modeling of low-level ISA semantics, including subtle architectural corner cases.
%
At the same time, the system must preserve correctness while actively modifying executable code, rather than merely analyzing or validating it.

These challenges distinguish ArmCFI, and more broadly static binary rewriting, from two representative approaches to formally verifying binary programs.
Certified compilers (\eg CompCert~\cite{compcert}) prove semantic preservation from sources to binaries using machine-checked proofs, but rely upon source-only information (\eg, types, lexical scopes, structural well-formedness) and only support binary features generated by a particular compiler.
Verified verifiers (\eg RockSalt~\cite{rocksalt}) prove safety of dynamic unit-testers designed to detect runtime failures of code-generators, but do not verify the transformations that produce them or provide developers a capability to implement a verifiably correct code transformation.

In contrast, \pname operates directly on existing binaries, verifying the correctness of the rewriting transformation itself and ensuring that generated binaries satisfy security properties by construction.
%\kjee{I want to say sth about \Picinae{} here.}
To achieve this, it leverages \Picinae's capability to specify theorems and write proofs about non-concrete binary codes that appear in specifications as variables $c$ with constraints $P(c)$.
For example, constraint $P(c)\equiv(\exists c_0,\ r(c_0)\,{=}\,c)$ specifies that code $c$ is an output of rewriter $r$.
A proof that $c$ is safe can therefore exclude from consideration any code that it can prove $r$ never generates.

In the following, we motivate the problem with a class of bugs that elude even experienced developers and resist exhaustive dynamic testing, then discuss our design scope and threat model.

\subsection{Motivation: ARM Unpredictable Behavior}

A CFI binary rewriter performs inherently complex transformations on executable code.
These include rewriting control-flow instructions (\eg branches), relocating and
reassembling both original and newly generated code segments, and embedding auxiliary
structures such as policy tables. As a result, producing a rewritten binary that is
both compliant with the underlying ISA specification \emph{and} faithful to CFI
safety requirements is nontrivial.

In particular, a CFI-enforcing binary rewriter must guarantee that every generated
instruction sequence remains fully compliant with the target ISA\@. However,
establishing such assurance through dynamic testing alone is fundamentally limited.

Like other ISAs, the ARM architecture explicitly defines \emph{unpredictable}
behaviors: execution outcomes that are left deliberately unspecified. These arise
from design choices intended to preserve implementation flexibility, to avoid
over-specifying invalid or ill-formed programs, and to balance performance with
backward compatibility. From a verification perspective, unpredictable behavior
introduces significant challenges: it induces semantic nondeterminism, necessitates
conservative over-approximation, and complicates the establishment of precise
correctness guarantees.

In practice, many CPU implementations handle such cases by trapping or terminating
execution, though the specification mandates no single outcome. Accordingly,
compilers and toolchains typically avoid generating instruction sequences that may
trigger unpredictable behavior. \pname{} explicitly disallows any rewritten binary
that could trigger such behavior.

This requirement motivates the use of formal verification in \pname{}: it ensures
that rewriting never introduces execution paths that enter architecturally
unpredictable regions. Achieving this guarantee is beyond the reach of conventional
dynamic testing, which explores only observed paths and cannot rule out problematic
sequences by construction. In contrast, formal verification enables proactive
identification of all such paths, allowing Cornerstone defense against control hijacking attacks, achieving widespread deployment with strong guarantees and near native overhead. However, the community has focused on design level guarantees, runtime overhead and policy generation largely overlooking implementation correctness and relying instead on dynamic testing. A more fundamental approach, formally verifying CFI implementations against safety and security specifications, remains largely unexplored. We need to be careful here to identify the overlook problem as developing guaranteed correct CFI implementations, not merely the problem of finding bugs in deployed CFI implementations.

\subsection{Threat Model and Research Scope}

\heading{Threat model.}
Unlike prior work that verifies either compilers (\ie source-to-binary transformations) or validators (\ie binary-to-accept/reject decisions), \pname{} verifies a \emph{binary-to-binary transformation} that enforces security properties directly on arbitrary inputs.
%
\pname targets adversaries who exploit memory corruption vulnerabilities to hijack program control flow, a threat model consistent with prior work on code-reuse attacks. We assume the attacker can corrupt code pointers (return addresses, function pointers, or vtable entries) and possesses a writable memory region under their control (\eg a heap object or auxiliary buffer). We further assume the attacker can perform limited memory disclosure sufficient to infer code and data addresses in the presence of ASLR\@.
Under \pname's CFI enforcement, any control-flow transfer that violates the policy is redirected to \texttt{abort()}, preventing attacker-controlled diversion of execution.

\heading{Research scope.}
We target the ARMv7 ISA for three reasons. First, ARMv7 represents one of the most
widely deployed architectures by installed base, particularly in low-powered embedded
and IoT devices that are commonly deployed without modern security defenses, making
binary hardening for this platform practically important. Second, a formal
specification for the ARMv7 instruction decoder exists and has been the subject of
substantial prior work on formal verification of instruction decoding, providing a
solid semantic foundation. Third, by targeting a fixed-width instruction encoding,
we avoid the variable-length decoding complexities of x86, allowing us to focus
formal reasoning effort on the binary rewriter itself rather than the decoder.

\pname covers subset of ARMv7 features to ensure sound rewriting while preserving practical applicability and coverage. Unsupported instructions are conservatively replaced with a branch to a safe abort handler. First, we assume a fixed endianness and disallow runtime changes to the CPSR E bit, as such changes could corrupt control-flow targets loaded from policy tables.
%
We also restrict execution to the ARM instruction set and exclude Thumb, Jazelle, and ThumbEE modes to avoid unintended state transitions and additional encoding complexity; all control-flow targets are aligned to prevent implicit mode switching.
%
Finally, we detect and eliminate all \unpredictable{} instructions, whose undefined semantics could otherwise introduce unintended or unsafe control flow.
%
\autoref{sec:overview} provides further details on these architectural features and the rationale behind these design choices.

% \heading{Problem setting.}
This work explores the formal verification of binary rewriter that operate on arbitrary binaries. Specifically, we focus on ELF binaries and restrict our reasoning to the \texttt{.text} section, the executable instruction stream. Other components, such as metadata, relocation entries, and dynamic linking structures. These may affect program behavior but fall outside our current scope.


The current implementation targets statically linked, non-PIE ARM binaries, in which all control transfers are self-contained and symbol references use absolute addresses. Extending coverage to PIE and dynamically linked binaries is achievable with additional engineering effort, and we leave it for future work.
