\subsection{Motivation: ARM Unpredictable Behavior}\label{sec:cfi_motivation}

A CFI binary rewriter performs complex transformations on executable code. It rewrites control-flow instructions, relocates and reassembles both original and generated code, and embeds auxiliary structures such as policy tables. Producing a rewritten binary that remains compliant with the target ISA while preserving CFI safety guarantees is therefore nontrivial.
%
%Dynamic testing alone cannot establish this level of correctness. \ixb{I don't like introducing dynamic testing so deep into the paragraph with one sentence to go. I like it this way where testing is mentioned at the end, right where it fits, and then ``Dynamic'' testing is defined 3 paragraphs below.}
A CFI-enforcing rewriter must ensure that all generated instruction sequences comply with the ISA, not just those exercised during testing.

A key challenge arises from \unpredictable behaviors in the ARM architecture~\cite{unpredictable_behaviors}. The ISA deliberately leaves certain execution outcomes unspecified to preserve implementation flexibility, avoid over-specifying ill-formed programs, and maintain backward compatibility. These behaviors introduce semantic nondeterminism, force conservative reasoning, and frustrate implementation independent correctness guarantees.

In practice, many CPU implementations handle such cases by trapping or terminating execution, although the specification does not mandate a single outcome. As a result, compilers and toolchains avoid emitting instruction sequences that may trigger unpredictable behavior. \pname adopts the same discipline: it does not generate binaries that could enter architecturally \unpredictable regions.

This requirement motivates formal verification. Dynamic testing explores only observed execution paths and cannot rule out latent violations. For a binary CFI rewriter, testing is further hindered by a combinatorial\wc{compounding} input space spanning (1) the input binary, (2) the CFI policy defining valid control transfers, (3) runtime inputs to the program, and (4) the ISA implementation. Exercising through testing all corner cases that may trigger unpredictable behavior across these dimensions is therefore infeasible.

In contrast, formal verification reasons over all possible executions, ensuring that rewriting never introduces paths that trigger unpredictable behavior. More broadly, although CFI is widely deployed with low overhead, prior work has focused on design guarantees, performance, and policy generation, largely overlooking implementation correctness. Formal verification of CFI implementations against precise safety and security specifications remains underexplored. Section~\ref{sec:case_studies} presents three concrete error cases that surfaced during verification and would be difficult to detect through testing alone.

\subsection{\pname Overview}

\autoref{fig:cfi_verif} illustrates the high-level workflow of \pname. To build a verified rewriter, we organize the system into three components.

\heading{ARMv7 decoder and lifter.} The rewriter's frontend component decodes byte sequences extracted from the \texttt{.text} section of well-formed ELF binaries. Within the soundness proof, the lifter \emph{lifts} the rewritten code into \Picinae's \IL, enabling symbolic reasoning over arbitrary binary inputs.

We target the ARMv7 ISA because it admits a formal specification~\cite{armv7formalization}, making it amenable to rigorous reasoning.
{% NOTE (@kjee) maybe redundant.
    In contrast, ISAs such as Intel x86 exhibit substantial semantic complexity and irregularity, which complicate full formalization.
}
ARMv7 therefore provides a practical foundation for machine-checked reasoning at the binary level.
%
While their correctness remains critical to end-to-end soundness, we do not verify the decoder or lifter in this work. Instead, we treat them as trusted components, as they have been extensively studied in prior work~\cite{bap, liblisa, armv8semantics1, armv8semantics2, armv8semantics3, armv8semantics4} (\autoref{sec:fm_related}).\kjee{citations needed.}


\heading{Binary CFI Rewriter.} \pname{} takes as input (1) a decoded ARMv7 instruction stream and (2) a user-provided policy specification (\eg{} permitted control-flow transfers) derived from static analysis or profiling. It instruments the program with CFI enforcement logic and produces a rewritten \texttt{.text} segment together with a policy table.
%
This component is the primary focus. We formally verify two properties for rewritten binaries:
%
\begin{itemize}[topsep=0pt,itemsep=-1ex,partopsep=1ex,parsep=1ex, leftmargin=*]
  \item \emph{CFI compliance} enforces the \wc{specified} control-flow integrity policy, and
  \item \emph{ISA compliance} preserves well-defined ARMv7 semantics and introduces no invalid or undefined behaviors.
\end{itemize}

We formalize these safety and security properties as ISA-level specifications that apply uniformly to all binaries. Once defined, they do not depend on a particular input program or rewriter instance.

\heading{\ELFPackager.} The final stage packages the rewritten code into an executable integrating\wc{combining} rewritten and original \texttt{.text} sections, policy tables and sundry metadata from the original binary.  We implement this step as a Python script using the LIEF library~\cite{lief} and treat it as out of scope. We discuss its limitations and potential hardening strategies in \autoref{sec:elf_packager_fm}.

\heading{Challenges of verifying binary rewriting.}
Formal reasoning about static binary rewriting (\ie binary-to-binary transformations) presents fundamental challenges. The input space is vast and highly irregular, lacking the structural guarantees available at the source level. Verification requires precise modeling of low-level ISA semantics, including subtle architectural corner cases. At the same time, the system must preserve correctness while actively modifying executable code, rather than merely analyzing or validating it.\kjee{At least, AFAIK, We don't care about program semantic here.}

These challenges distinguish \pname, and more broadly static binary rewriting, from two representative approaches to formally verifying binary programs.
%
Certified compilers (\eg CompCert~\cite{compcert}) prove semantic preservation from sources to binaries using machine-checked proofs, but rely on source code availability and only support binary features generated by a particular compiler,\kjee{can we say that subset compiler features?} precluding their use on legacy systems and code with unconventional instruction sequences.
%
Verified verifiers (\eg RockSalt~\cite{rocksalt}) prove safety of dynamic unit-testers designed to detect runtime failures of code-generators, but do not verify the transformations that produce them or provide developers a capability to implement a verifiably correct code transformation.

In contrast, \pname operates directly on existing binaries, verifying the correctness of the rewriting transformation itself and ensuring that generated binaries satisfy security properties by construction.
%
To achieve this, it leverages \Picinae's capability to specify theorems and write proofs about symbolic binary codes that appear in specifications as variables $c$ with constraints $P(c)$.
For example, constraint $P(c)\equiv(\exists c_0,\ r(c_0)\,{=}\,c)$ specifies that code $c$ is an output of rewriter $r$.
  A proof that $c$ is safe can therefore analyze rewriter $r$ to prove that executions of unknown code $c$ exclude unsafe behaviors.

\subsection{Threat Model and Research Scope}

\ixb{Tricky things to include ($\sim$21:30): basically attackers get to send inputs to victim programs and send malware to the CFI rewriter, out of scope is messing with the hardware, ELF metadata, and manipulating the policy input.}

\heading{Threat model.}
Unlike prior work that verifies either compilers~\cite{compcert} (\ie source-to-binary transformations) or validators~\cite{rocksalt} (\ie binary-to-accept/reject decisions), \pname{} verifies a \emph{binary-to-binary transformation} that enforces security properties directly on arbitrary inputs.
%
\pname targets adversaries who exploit memory corruption vulnerabilities to hijack program control flow, a threat model consistent with prior work on code-reuse attacks. We assume the attacker can corrupt code pointers (return addresses, function pointers, or vtable entries) and possesses a writable memory region under their control (\eg a heap object or auxiliary buffer). We further assume the attacker can perform limited memory disclosure sufficient to infer code and data addresses in the presence of ASLR and supply maliciously crafted binaries.
Under \pname's CFI enforcement, any control-flow transfer that violates the policy is redirected to the safe abort (\ie \texttt{abort()}), preventing attacker-controlled diversion of execution.

\heading{Research scope.}
We target the ARMv7 ISA for three reasons. First, ARMv7 represents one of the most
widely deployed architectures by installed base~\cite{arm_field_growth,patterson2016computer}, particularly in low-powered embedded
and IoT devices that are commonly deployed without modern security defenses, making
binary hardening for this platform practically important. Second, a formal
specification for the ARMv7 instruction decoder has been the subject of
substantial prior work on formal verification of instruction decoding, providing a
solid semantic foundation. Third, by targeting a fixed-width instruction encoding,
we avoid the variable-length decoding complexities of x86, allowing us to focus
formal reasoning effort on the binary rewriter itself rather than the decoder.

Although \pname strives to behaviorally preserve near-arbitrary policy-compliant binaries, it conservatively abandons the preservation goal when necessary to ensure safety.
For example, we disallow runtime changes to the CPSR E bit to enforce fixed endianness, as endianness changes could corrupt control-flow targets loaded from policy tables.
%
We also restrict execution to the ARM instruction set and exclude Thumb, Jazelle, and ThumbEE modes to avoid unintended state transitions and additional encoding complexity; all control-flow targets are aligned to prevent implicit mode switching.
%
Finally, we detect and replace all \unpredictable{} instructions with safe aborts, since their undefined semantics could introduce unintended or unsafe control flows.

This work explores the formal verification of a rewriter that operates on binary code sections. Specifically, we focus on securing the \texttt{.text} sections of ELF binaries. Securing non-code ELF components, such as metadata, relocation entries, and dynamic linking structures, falls outside our current scope.
%
The current implementation targets statically linked, non-PIE ARM binaries, in which all control transfers are self-contained and symbol references use absolute addresses. Extending coverage to PIE and dynamically linked binaries is achievable with additional engineering effort, and we leave it for future work.
