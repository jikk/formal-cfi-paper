\subsection{Formally Verified Binary Rewriting}

We position the research and discuss design space.

\comment{%
- **Positioning and scope.**
  ARMCFI is, to our knowledge, the first work to formally verify a *program transformation* (i.e., a static binary rewriter) that takes arbitrary binaries as input and produces security-hardened outputs that provably comply with a precise safety specification.

- **Problem setting.**
  We study the problem of formally verifying a system that operates on *arbitrary binaries*.
  - In this work, we focus on arbitrary *ELF* binaries.
  - Within each binary, we restrict our analysis to the `.text` section (i.e., executable instruction streams).
  - Other components of the binary (e.g., metadata, relocation, dynamic linking) may affect overall behavior, but we treat them as out of scope.

- **Challenges of the domain.**
  Formal methods for programs that consume and transform arbitrary binaries remain rare and challenging.
  - The input space is vast and highly irregular.
  - Reasoning requires precise, low-level ISA semantics.
  - The system must preserve correctness while modifying executable code, not just analyze or validate it.

- **Relation to prior work.**
  We contrast ARMCFI with two representative lines of work:

  - **CompCert (verified compilation).**
    CompCert is a seminal verified C compiler that proves semantic preservation from source to target code using machine-checked proofs.
    - It replaces testing-based confidence with formal guarantees and produces efficient code.
    - However, it assumes well-defined source programs (i.e., no undefined behavior) and operates on source-level inputs rather than arbitrary binaries.
    - In contrast, ARMCFI works directly on existing binaries and verifies the correctness of a *rewriting transformation*, rather than compilation from a high-level language.

  - **RockSalt (verified validation).**
    RockSalt verifies a validator that enforces software fault isolation (SFI) for x86 binaries.
    - It guarantees that any binary accepted by the validator satisfies the sandboxing policy.
    - However, it does not verify the *rewriter* that produces such binaries; instead, it assumes untrusted code and checks it at load time.
    - ARMCFI complements this approach by verifying the transformation itself, ensuring that the generated binaries satisfy the intended security properties by construction.
}

\pname targets adversaries who exploit memory corruption vulnerabilities to hijack program control flow, a threat model consistent with prior work on code-reuse attacks. We assume the attacker can corrupt code pointers (return addresses, function pointers, or vtable entries) and possesses a writable memory region under their control (\eg a heap object or auxiliary buffer). We further assume the attacker can perform limited memory disclosure sufficient to infer code and data addresses in the presence of ASLR\@.
Under \pname's CFI enforcement, any control-flow transfer that violates the policy is redirected to \texttt{abort()}, preventing attacker-controlled diversion of execution.

The current implementation targets statically linked, non-PIE ARM binaries, in which all control transfers are self-contained and symbol
references use absolute addresses. Extending coverage to PIE and dynamically linked binaries is achievable with additional engineering effort, and we leave it for future work.
