\section{Formal Verification of CFI Binary Rewriter}
\label{sec:back}

\pname formally verifies a program transformation: a static binary rewriter that takes arbitrary binaries as input and produces security-hardened outputs guaranteed to satisfy a precise safety specification.
\kjee{Specifically, CFI specification and ISA specification.}
The precise specification is universal to all binary code for the ISA; once written, it never needs to be specialized to a new rewriter.

Formal reasoning about static binary rewriting (\ie binary-to-binary transformations) presents fundamental challenges. The input space is vast and highly irregular, lacking the structural guarantees available at the source level. Verification requires precise modeling of low-level ISA semantics, including subtle architectural corner cases.
%
At the same time, the system must preserve correctness while actively modifying executable code, rather than merely analyzing or validating it.\kjee{At least, AFAIK, We don't care about program semantic here.}

These challenges distinguish \pname, and more broadly static binary rewriting, from two representative approaches to formally verifying binary programs.
%
Certified compilers (\eg CompCert~\cite{compcert}) prove semantic preservation from sources to binaries using machine-checked proofs, but rely on source code availability and only support binary features generated by a particular compiler,\kjee{can we say that subset compiler features?} precluding their use on legacy systems and code with unconventional instruction sequences.
%
Verified verifiers (\eg RockSalt~\cite{rocksalt}) prove safety of dynamic unit-testers designed to detect runtime failures of code-generators, but do not verify the transformations that produce them or provide developers a capability to implement a verifiably correct code transformation.

In contrast, \pname operates directly on existing binaries, verifying the correctness of the rewriting transformation itself and ensuring that generated binaries satisfy security properties by construction.
%
To achieve this, it leverages \Picinae's capability to specify theorems and write proofs about symbolic binary codes that appear in specifications as variables $c$ with constraints $P(c)$.
For example, constraint $P(c)\equiv(\exists c_0,\ r(c_0)\,{=}\,c)$ specifies that code $c$ is an output of rewriter $r$.
A proof that $c$ is safe can therefore analyze rewriter $r$ to prove that executions of unknown code $c$ exclude unsafe behaviors.

In the following, we motivate the problem with a class of bugs that elude even experienced developers and resist exhaustive dynamic testing, then discuss our research scope and threat model.

For example, the ARM ISA specification defines certain encodings of the \texttt{STR} immediate instruction as \unpredictable{}~\cite{unpredictable_behaviors,examiner2024asplos}: the execution outcome is deliberately unspecified and may differ between implementations.
Most ARM implementations execute the instruction identically, but a few raise exceptions that change the program's control-flow.
Dynamic testing of a CFI rewriter that preserves \texttt{STR} immediate instructions as security-irrelevant may therefore incorrectly conclude that such a rewriter is safe until tested on a rare implementation of the ISA\@.
Even when all current implementations behave consistently, future ARM processors might differ, making the rewriter unsafe for long-term deployment.

Binary rewriter implementation errors are also difficult to detect when they manifest only for rare input binaries, such as malware crafted by an attacker to violate the policy.
For example, our first implementation of \pname{} generated rewritten binaries containing a jump table that included an entry for each function entry point in the input binary.
This unverified implementation passed all dynamic tests until our attempts to formally verify it uncovered a corner case:
a maliciously crafted input binary with many densely packed function entry points could overflow the available space for the jump table, causing rewritten code to reference non-table bytes as policy data and break out of the sandbox.
Our failed attempts to formally prove soundness of this early version uncovered the bug and allowed us to fix it.

These experiences illustrate the difficulties that dynamic testing approaches face when the input space is large and complex (\eg, arbitrary binary code).
In contrast, FM approaches reliably detect such bugs because the proof does not rely on input testing.
Theorems are universally quantified over arbitrary input binaries, not merely those produced by well-behaved tools;
and analysis of arbitrary code within a proof environment entails abstract symbolic evaluation against an ISA specification, not any particular implementation of the ISA\@.

\subsection{Threat Model and Research Scope}

\heading{Threat model.}
Unlike prior work that verifies either compilers (\ie source-to-binary transformations) or validators (\ie binary-to-accept/reject decisions), \pname{} verifies a \emph{binary-to-binary transformation} that enforces security properties directly on arbitrary inputs.
%
\pname targets adversaries who exploit memory corruption vulnerabilities to hijack program control flow, a threat model consistent with prior work on code-reuse attacks. We assume the attacker can corrupt code pointers (return addresses, function pointers, or vtable entries) and possesses a writable memory region under their control (\eg a heap object or auxiliary buffer). We further assume the attacker can perform limited memory disclosure sufficient to infer code and data addresses in the presence of ASLR\@.
Under \pname's CFI enforcement, any control-flow transfer that violates the policy is redirected to \texttt{abort()}, preventing attacker-controlled diversion of execution.

\heading{Research scope.}
We target the ARMv7 ISA for three reasons. First, ARMv7 represents one of the most
widely deployed architectures by installed base~\cite{todo}, particularly in low-powered embedded
and IoT devices that are commonly deployed without modern security defenses, making
binary hardening for this platform practically important. Second, a formal
specification for the ARMv7 instruction decoder has been the subject of
substantial prior work on formal verification of instruction decoding, providing a
solid semantic foundation. Third, by targeting a fixed-width instruction encoding,
we avoid the variable-length decoding complexities of x86, allowing us to focus
formal reasoning effort on the binary rewriter itself rather than the decoder.

Although \pname strives to behaviorally preserve near-arbitrary policy-compliant binaries, it conservatively abandons the preservation goal when necessary to ensure safety.
For example, we disallow runtime changes to the CPSR E bit to enforce fixed endianness, as endianness changes could corrupt control-flow targets loaded from policy tables.
%
We also restrict execution to the ARM instruction set and exclude Thumb, Jazelle, and ThumbEE modes to avoid unintended state transitions and additional encoding complexity; all control-flow targets are aligned to prevent implicit mode switching.
%
Finally, we detect and replace all \unpredictable{} instructions with safe aborts, since their undefined semantics could introduce unintended or unsafe control flows.
\Autoref{sec:overview} provides further details on these architectural features and the rationale behind these design choices.

This work explores the formal verification of a rewriter that operates on binary code sections. Specifically, we focus on securing the \texttt{.text} sections of ELF binaries. Securing non-code ELF components, such as metadata, relocation entries, and dynamic linking structures, falls outside our current scope.
%
The current implementation targets statically linked, non-PIE ARM binaries, in which all control transfers are self-contained and symbol references use absolute addresses. Extending coverage to PIE and dynamically linked binaries is achievable with additional engineering effort, and we leave it for future work.
