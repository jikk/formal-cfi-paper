\subsection{Case studies}\label{sec:case_studies}
Formal verification exposed several implementation errors that evaded design-level verification and dynamic testing during our development.
We present three representative case studies.
Each arises from a corner case that is easy to overlook in implementation, difficult to trigger through dynamic testing, yet cannot escape systematic proof. The first case stems from the inherent complexity of binary rewriting, while the latter two arise from obscure instructions and \unpredictable{} behaviors in the ARMv7 ISA\@.

Across all cases, the proof obligations force reasoning over all possible inputs and executions, exposing violations that remain latent under conventional testing.

The rewriter maintains both the original and rewritten text segments, making address translation between them subtle.
% A natural implementation of the translation function $\itoip$ leaves indices outside the original text segment unchanged, mirroring the inverse mapping $\iptoi$.
%This behavior appears reasonable and aligns with common co-allocation designs used in static binary rewriting. 
%However, it implicitly assumes that such indices are benign, overlooking the possibility that they may refer to attacker-controlled locations in the rewritten code.
A natural implementation of the translation function $\itoip$ only remaps original text segment indices to corresponding new text segment indices, leaving other indices unchanged.

\autoref{fig:address_translation} illustrates how this can lead to a subtle yet critical vulnerability.
If the original policy $\Pol$ permits a jump to an external address that becomes part of the new text section during rewriting (due to section insertion and resizing), the $\itoip$ implementation above fails to accurately reflect the \emph{reinterpreted policy} defined by $\Pol\kern1pt'$ for the rewritten binary.
This allows the policy table to contain an arbitrary new text section address that does not start a \Block.
An attacker can abuse this to manipulate a guarded indirect branch into directly stepping to another indirect branch, bypassing the guard code and violating the policy.

This vulnerability evaded dynamic testing because it is only exhibited by carefully crafted binary code inputs not included in typical test sets.
It evades design-level verification because the error is in the low-level implementation of the rewriter, not the high-level algorithm it is intended to implement.

\heading{Branching to PC.}
Most ARMv7 instructions treat the \PC as an invalid operand, resulting in \unpredictable{} behavior. Our rewriter implementation therefore removes most, but instruction \cd{BX\:pc} is a subtle exception that must be preserved. It has a valid semantics in ARM mode (even though it behaves as an inefficient form of branch~\cite{gas_manual}) because it is useful for quickly switching from Thumb to ARM mode.

However, rewriting \cd{BX\:pc} like other \cd{BX} instructions results in policy-violating rewritten code because it generates a \Block containing other instructions (\eg \cd{UBFX}) for which PC operands are \unpredictable.
This error was not caught by dynamic testing because \cd{BX\:pc} is a rare instruction not generated by compilers targeting ARM mode, and not all ARMv7 hardware or emulators reliably exhibit any unusual behavior when the resulting \Block executes.

During formal verification, symbolic evaluation against the ISA specification semantics yields a proof state that is nondeterministic, preventing the proof from progressing.
To fix it, we added code to explicitly recognize and handle \cd{BX\:pc} as a special case during rewriting. Instead of applying the generic instrumentation, we rewrite it into a semantically equivalent, well-defined sequence (\eg a direct branch) that avoids \unpredictable{} uses of \PC\@. This ensures that the rewritten code remains within the defined subset of the ISA and preserves control-flow integrity.

\heading{Misaligned \PC loads.}
ARMv7 specifies that loading a pointer into the \PC from a misaligned address causes \unpredictable{} behavior.
Our early implementation of \pname carefully aligned source addresses for most \PC loads, but not for returns, which load \PC addresses from the stack pointer address.
Stack pointers remain aligned for all binaries that obey the ARM standard calling conventions, so this vulnerability was not detected during testing.
However, formal verification revealed that symbolic interpretation of a return instruction in an abstract machine state with arbitrary stack pointer value yields a nondeterministic state, making soundness unprovable for that implementation.

To fix this, our verified implementation modifies the generated code to enforce alignment explicitly before performing the load. This involves realigning the stack pointer or masking the address to ensure word-alignment prior to loading into the \PC. By eliminating dependence on external invariants, the rewritten code becomes robust to adversarial inputs that violate the calling conventions, and satisfies the proof obligations.
