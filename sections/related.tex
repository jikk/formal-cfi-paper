\section{Related Work}

CFI enforcement is a very active field of research with many new publications each year, each supporting the correctness of their work using one or more of three approaches~\cite{cracks_in_shields}: theoretical verification, experimental verification or quantitative analysis.
% A 2020 survey~\cite{cracks_in_shields} of 50 CFI solutions found they each evaluated their methods using one of three approaches: theoretical verification, experimental verification or quantitative analysis.
Theoretical verification comprises informal analyses of the CFI solution (e.g., \texttt{SAFEDISPATCH}~\cite{safedispatch}),
experimental verification includes applying the CFI technique to vulnerability test-suites (e.g., RIPE~\cite{suite_ripe} or RecIPE~\cite{suite_recipe}) or other software with known vulnerabilities (e.g., CVEs),
and quantitative analysis involves measuring a static property of programs before and after treatment, such as number of code gadgets or average indirect target reduction (AIR)~\cite{bincfi}.

Formal verification of low-level code has received increasing attention recently.
Most projects have created general purpose binary analysis frameworks, but some have tailored solutions to specific problems, such as certified decompilation~\cite{formally_verified_lifting} and binary pointer analysis~\cite{verified_pointers}.
Islaris~\cite{islaris} reasons about concrete program traces using the Isla symbolic interpreter to create trusted traces from the target architecture's Sail specification.
IsaBIL~\cite{isabil} translates BAP~\cite{bap} decompilations into its Isabelle/HOL embedding to reason about concrete program executions.
Most recently, a team published a relational Hoare logic in HOL Light and used it to prove program equivalence and correctness~\cite{relational_realistic}.
Of these, only the last is capable of quantifying over programs, as we have done, because it uses a decode function to interpret bytes from memory.
