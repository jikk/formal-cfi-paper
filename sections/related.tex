\subsection{\cfi with Static Binary Rewriting}\label{sec:cfi_related}
% rewriting this because it's AI'd
% CFI is a foundational security defense designed to protect against control hijacking attacks by restricting the set of valid control-flow transfers a program may execute at runtime.
% The level at which CFI is enforced depends on the available program representation. When source code is accessible, CFI is typically implemented as a compiler pass, optionally leveraging hardware support such as Intel CET/PT for enforcement~\cite{ptcfi,ptcfi2}. When only a binary is available, CFI can be enforced via either dynamic instrumentation or static binary rewriting.
CFI~\cite{abadi_cfi,burow2017survey} is a static defense for defending against control-flow hijacking attacks.
Control-flow policies encode a whitelist of permitted control-flow edges.
The policy is enforced by adding security guards that check impending jump targets against the policy.
CFI can be applied to both source and binary code, optionally leveraging hardware support~\cite{ptcfi,ptcfi2}.
At the binary level, CFI is applied either via static binary rewriting or dynamic instrumentation.

Although dynamic instrumentation is precise, it is generally less favored due to its runtime overhead and transparency limitations.
Lightweight, source-free CFI implementations include kBouncer~\cite{kbouncer}, ROPecker~\cite{ropecker}, and ROPGuard~\cite{ropguard}. kBouncer and ROPecker rely on the LBR to analyze chains of gadgets, with ROPecker using data from static binary analysis to project future control flows.
Despite defending against many ROP attacks, some attacks still succeed by flushing the LBR or breaking the gadget threshold~\cite{coarse_cfi}.

% "
% Static binary rewriting is more efficient in practice, as instrumentation is limited to control-transfer instructions rather than the full instruction stream. The underlying challenge, however, lies in constructing a complete and accurate control-flow policy from the binary alone, a problem widely recognized as difficult and, in many cases, undecidable. Static binary rewriting CFIs also struggle with high overheads from instruction instrumentation. This research specifically focuses on the correct implementation of binary-only CFI enforced through static binary rewriting. Other aspects, such as the generation of control-flow policies or optimization of runtime efficiency, are outside the scope of this work.
Static binary rewriting is typically more performant than dynamic instrumentation~\cite{static_cfi_perf,russo2010dynamic}, invoking only a small number of additional instructions per jump for CFI enforcement.
It is substantially more challenging to generate control-flow policies for binary programs, however.
Constructing control-flow policies is known to be undecidable in the general case~\cite{cfi2005ccs}.
Our work assumes a trusted control-flow policy and proves the soundness of a static rewriter's enforcement of it, leaving policy-generation to related work.

Early CFI works implement coarse-grained policies on source-free binary code~\cite{ccfir,bincfi}.
BinCFI places jump targets in a bitmap and adds guards to all indirect jump instructions to enable lookups.
For every indirect jump, it checks whether target addresses are call-preceded of a part of a permissible target list.
CCFIR works with relocation data, rerouting indirect jumps to a separate springboard section.
While that offers an additional layer of protection from ROP attacks, both CCFIR and binCFI were shown vulnerable to advanced ROP attacks due to policy imprecision~\cite{outofcontrol}.

CFIs using basic blocks are a low overhead option as well~\cite{bbb_cfi}.
Similar to our work, jumps are permitted only if the destination address is an entry point of a basic block.
This policy is enforced with a monitor using Intel PT to gather control-flow data in real time.
BinCC~\cite{bincc} is also similar to this implementation, dividing code into code continents instead of basic blocks.

Due to its effectiveness, CFI has been widely adopted in practice. Modern processors provide hardware support for coarse-grained CFI to reduce overhead~\cite{isacfi2019hasp,liljestrand2019pac}, while enabling extensions to finer-grained, policy-driven enforcement such as that implemented by \pname. As a result, many practical aspects of CFI deployment in real-world systems have been extensively explored~\cite{becker2024woot}.

Recent work such as $\mu$CFI~\cite{ceesay2024mucfi}  extends CFI enforcement into the microarchitectural domain. It defines a security property over cycle-level \PC updates and formally verifies that processor microcode enforces CFI even under speculative execution and timing-based behaviors.
%
The proof guarantees that all indirect control transfers resolve to destinations permitted by a control-flow graph capturing correct hardware behavior. However, these guarantees are orthogonal to software-level CFI policies and do not address how such policies are constructed or enforced at the binary level.

Recent advances in \emph{formally verified lifting} have opened new avenues for formally verified binary analysis, enabling verification of both correctness and security properties~\cite{scalable_binary_lifter_validation,formally_verified_lifting,holba_sound_transpilation,verbeek2024verifiably}.
However, existing frameworks focus on verifying concrete binaries and have limited support for properties of binary code in which some or all instructions are symbolic unknowns. This limits their applicability for verifying binary-to-binary code rewriters.

Certified compilation~\cite{compcert,jasmin,barthe2019formal} reasons about non-concrete binary programs from source code, with the goal of proving compiler correctness through semantic transparency.
These approaches typically rely upon translating source-level typing information through \IL representations to compiled binaries.
This yields verified code from a particular source language and compiler toolchain.

\Picinae{}~\cite{picinae} builds upon Rocq to model machine code execution through memory state and execution traces, and represents program state symbolically, permitting proofs to treat the code as a proof variable.
This enables verification results to generalize from a single program to the unbounded set of binaries a rewriter may encounter.
Recent works have applied it to formally verify fault-tolerance of binary codes~\cite{averill26bar}, and security-critical timing properties of RTOS and cryptographic binaries~\cite{averill2025src}.
