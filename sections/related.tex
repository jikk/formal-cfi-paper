CFI is a foundational security defense designed to protect against control hijacking attacks by restricting the set of valid control-flow transfers a program may execute at runtime. The level at which CFI is enforced depends on the available program representation. When source code is accessible, CFI is typically implemented as a compiler pass, optionally leveraging hardware support such as Intel CET for enforcement.~\cite{bibitem}[cite1][cite2] When only a binary is available, CFI can be enforced via either dynamic instrumentation or static binary rewriting. 

Although dynamic instrumentation is precise, it is generally less favored due to its runtime overhead and transparency limitations.
Runtime lightweight, source-free CFI implementations include kBouncer, ROPecker, and ROPGuard. kBouncer and ROPecker rely on the LBR to analyze chains of gadgets, with ROPecker taking data from static binary analysis to project future control flow as well. [cite8] [cite9] [cite10]
 Despite successfully defending against ROP chain attacks, Davi showed that these models are not fully sufficient as the attacker can flush the LBR or break the gadget threshold. [cite11]

Static binary rewriting is more efficient in practice, as instrumentation is limited to control-transfer instructions rather than the full instruction stream. The underlying challenge, however, lies in constructing a complete and accurate control-flow policy from the binary alone, a problem widely recognized as difficult and, in many cases, undecidable. Static binary rewriting CFIs also struggle with high overheads from instruction instrumentation. This research specifically focuses on the correct implementation of binary-only CFI enforced through static binary rewriting. Other aspects, such as the generation of control-flow policies or optimization of runtime efficiency, are outside the scope of this work.

Early CFI work in 2013 implemented coarse-grained policies on source-free binary code. CCFIR and binCFI are good examples of this, binCFI being the first to do so without relocation information as well.[cite4][cite5] binCFI places jump targets in a bitmap and adds guards to all indirect jump instructions to enable lookups. For every indirect jump, it checks whether target addresses are call-preceded of a part of its permissible target list. CCFIR works with relocation data, rerouting indirect jumps to a separate Springboard section. It also randomizes target entry locations within the Springboard as well. While that offers an additional layer of protection from ROP attacks, In 2014, Göktas [there are more authors here do we list them all] showed that both CCFIR and binCFI were proven vulnerable to advanced ROP attacks due to the "looser" nature of their policies. [cite3=outofcontrol] 

CFIs using basic blocks are a low-overhead option as well. [cite12] We utilize basic blocks in our enforcement

A more recent CFI project most similar to ours, muCFI, uses formal verification, proving an absence of hardware-based control flow attacks for a given CPU architecture.[cite7=mucfi] For a given CPU, all indirect jumps reach a valid destination defined by the CFG by keeping track of the PC value. However, while excellent at protecting against constant-time attacks and hardware-level control flow hijackings, software-related vulnerabilities, such as buffer overflows, are out of scope for muCFI.

Secure IRMs take an untrusted binary as input and produce a hardened, rewritten binary augmented with additional security checks. By weaving security logic into the original binary, IRMs partition program execution into two distinct contexts: the guest context, which runs the original program, and the monitor context, which enforces the security policy.

IRMs vary considerably in their statefulness. \kwh{Static} binary CFI is an instance of a stateless IRM, in which the control-flow policy remains fixed throughout program execution and does not require persistent monitor state. Stateful IRMs, by contrast, maintain internal monitoring state across execution, such as shadow memory for dynamic information flow tracking, allocation and deallocation histories for memory leak detection, and similar policies.

Although this challenge is orthogonal to the stateless enforcement of CFI addressed in this work, it represents a compelling direction for future research in formally verified binary rewriting, and we revisit it in \autoref{sec:disc}.

Recent advances in \emph{formally verified lifting} have opened new avenues for formally verified binary analysis, enabling verification of both correctness and security properties. However, existing frameworks reason over concrete binaries and cannot generalize to prove properties in which some or all the binary code is unknown. This limits their practical applicability to binaries known at verification time.

\kwh{[KWH] Formal verification of binary code in any form hasn't been around for very long (only a few years).  So let's not cast it as a well-established science.  Main thing to emphasize here is that apart from Picinae, all the systems take a complete, fully known binary code as input and verify it. They can't prove any property of binary code that isn't fully known at verification time.}

  Overcoming this limitation requires more than a proof assistant. Rather, it requires an abstraction layer that faithfully models real-world ISAs while supporting symbolic reasoning. \Picinae~\cite{picinae} provides this foundation. Built on Rocq, it models machine execution through memory state and execution traces and represents program state symbolically, allowing proofs that treat the binary itself as a variable. This enables verification results to generalize from a single program to the unbounded set of binaries a rewriter may encounter.

  This capability is essential for \pname. Frameworks that operate on concrete binaries can verify individual rewritten outputs but cannot prove that the rewriter is correct for all inputs. \Picinae~\xspace lifts reasoning from individual binaries to the rewriter’s behavior across all binaries, enabling the end-to-end correctness guarantees that \pname requires.
