A CFI rewriter \emph{implementation} is sound if all execution traces of all programs it outputs respect the input control flow policy.
We formalize this notion below.

\heading{Safety of a single trace.}
We define a proposition $Pol(i, j)$, which is true if stepping from index $i$
to $j$ is permitted by the policy.
In our case, since the policy is specified as a function from source indices to lists of valid destination indices,
$Pol(i, j) \equiv j \in pol(i)$.
For an execution trace to be safe, all steps must satisfy $Pol$:
\[
\safe{trace}(t) \equiv \forall (\langle a_1,\sigma_1\rangle, \langle a_2,\sigma_2\rangle) \in \mathit{steps}(t),
   \Pol(a_1/4, a_2/4)
\]
\optional{We do not care if the trace ends by throwing a hardware exception, so this definition only considers steps between two addresses.}

\heading{Safety of a trace in a rewritten program.}
% \ixb{@MAX: in equations, you need to wrap multi-letter variable and function names in mathit, mathtt, mathrm. If you do not they will be set as a product of the individual letters.
% Note the difference between $txt'$ and $\mathit{txt'}$.}
The previous definition does not account for the address translation done by the rewriting process.
Similar to \itoip (\autoref{sec:cfi_design}), we define a function \iptoi used to determine if steps in the rewritten program correspond to policy permitted steps in the original:
\[
  \iptoi(i') = \begin{cases}
    \mathit{\bi} + n & \text{if } i' \in [\bip, \bip + |\texttt{flatten}(\mathit{txt'})|-1], \\
    i'     & \text{otherwise.}
  \end{cases}
\]
where $n$ is the unique index such that $i'$ is in the $n$th block.
All indices contained in the new text segment are mapped to the corresponding index of the old text segment,
while other indices are left unchanged.
We must also account for the abort index and steps between instructions within the same block.
Thus, we can define a permitted step for a rewritten binary as:
\begin{align*}
  \Polp(i', j')     \equiv~ & j' = ai & & \textit{step to the abort handler}\\
                     \lor~ & \iptoi(i') = \iptoi(j') & & \textit{step within a block}\\
                     \lor~ & Pol(\iptoi(i'), \iptoi(j')) & & \textit{policy permitted step}
\end{align*}
and update our definition of a safe trace to use $Pol'$ instead of $Pol$.

Note, \Polp permits a rewritten block to step to its corresponding instruction in the old text segment
as \iptoi will return the same value for the old index, making the ``step within a block'' case true.
While mechanizing a proof that this does not happen is possible, we instead set the old text segment as nonexecutable.

\heading{Safety of a rewritten program.}
\ixb{@Max, what do you mean by ``the addresses provided as input by the user'' here? Policy? \bi, \bip, \tbi, \mai?}
A rewritten program can be described by the new text and table segments returned by the rewriter and the addresses provided as input by the user.
\[
   p' = (\txtp, \mathit{tbls}, \mathit{addrs})
\]
We can define a rewritten program to be safe if all traces that meet the following preconditions are safe:
(1) the trace starts in the ARM instruction mode
(2) the new text segment is placed in memory at the correct location \bip
(3) the table segment is placed in memory at the correct location \tbi in the correct endianness
(4) the new text and table segments are nonwritable 
and
(5) the starting address of the trace is the start of a block.

The rewriter only gets to determine the instructions placed in the new text segment;
we make no assumptions on what other executable code is placed in memory
(such as code provided by the kernel).
Therefore, we can no longer guarantee anything if the trace leaves the new text segment.
However, this can only happen if it was permitted by the original policy,
or if the destination is the abort handler.
Thus, we only consider the longest prefix of a trace that contains at most one address
outside of the new text segment (at the head of the trace).
\[
  \safe{prog}(p') \equiv \forall t, \mathit{Precond}_{p'}(t) \implies \safe{trace}(\mathit{prefix}(t))
\]

\heading{Soundness of a CFI implementation.}
For a CFI implementation to be sound, all rewritten programs produced by the rewriter must be safe.
\begin{align*}
  Sound(CFI) \equiv \forall \txt, \pol, \addrs, \txtp, \tbls, \\
    CFI(\txt, \pol, \addrs) = (\txtp, \tbls) \implies \safe{prog}(\txtp, \tbls, \addrs)
\end{align*}

Because we reason about the safety of unspecified\wc{symbolic, undetermined, quantified} programs we need an internal lifter to translate the program bytes to symbolically executable PIL statements.
To this end, we created the internal ARMv7 lifter, encoding the fetch-decode logic in the official documentation~\cite{ARMv7manual} as a Gallina function.

Some instructions and cpu modes result in undefined or unsupported behavior.
For example, the behavior of most instructions is undefined when they have \texttt{pc} as a register operand,
unaligned \texttt{pc} instruct-fetch is undefined,
and we only support ARM mode.
The lifter models unsupported and undefined instructions as \unpredictable{}, assigning unknown values to all registers, including \texttt{pc}.
While the lifter does not support these instructions and modes, the rewriter does, and the proof guarantees soundness even in their presence.

The soundness proof follows a co-inductive structure that boils down to proving each rewritten block is safe.
The new text segment is sliced up by defining an invariant point at every rewritten block entrance, hardware interrupt, and instruction outside of the rewritten block, that requires the trace to be safe.
Picin\ae{} slices the proof into two cases: the base case which requires us to reach and satisfy an invariant, and the inductive case which requires us to show that all internal invariants, execution reaches and satisfies a next invariant.
For our purposes, only the invariants at the start of blocks are internal invariants, as we provide no guarantees after a program makes a permitted jump out of the instrumented code section.
The inductive case gives us the invariant of the trace as a precondition, which means all steps in it are permitted.
A helper lemma proves that the tail of a safe trace does not influence whether it reaches and satisfies an invariant;
forgetting the tail we are left with a proof that starting at the beginning of a block we safely reach a next invariant.

or (3) raise a hardware exception, all while only taking permitted steps.
We define a block to be safe if all such traces have this property.

We can show that the invariants about memory will hold regardless of what happens in the rewritten code,
so we do so now.
For the nonwritable memory requirements, we show that the lifter never produces IL that modifies
memory permission bits (we are only concerned with User mode),
and therefore remain correct for all traces that start with the correct permissions.
Note that this implicitly assumes that the program does not ask the kernel to modify memory permissions,
so we cannot guarantee the safety of any rewritten program with this functionality.
For the invariants about the new text and table segments being located in the correct location in memory,
it is obvious that if we assume that the segments were in the correct location at the start of the trace,
and the segments are nonwritable, that they will continue to be in the correct location.
Thus, upon reaching an invariant point, we just need to prove that the trace only took permitted steps,
is still in ARM mode, and did not change the endianness flag
(since we only assume the table segment is in the same endianness as the CPU at the start of the trace).

Now that the problem has been reduced to only considering a single block, we just need to
consider the following cases:

\heading{Unchanged block.}
The corresponding block for most instructions just contains
the original instruction. We define an instruction to be safe if it can only
ever fall through to the next instruction or raise a hardware exception and can never change the
CPU's instruction mode or endianness. For these cases, we prove as a lemma that a block containing
a single safe instruction is safe as long as fallthrough is policy-permitted,
and that whenever the block remains unchanged,
the original instruction was a safe instruction where fallthrough is permitted.

\heading{Non-control-flow change.}
For instructions that are changed for non-control-flow reasons,
such as instructions that just reference the PC register without modifying it, we prove a
lemma similar to the previous case about blocks consisting entirely of safe instructions,
with one caveat that we must deal with.
Conditional instructions become blocks with a conditional branch at the start,
which is not a safe instruction, as it does not always fallthrough or raise an exception.
To handle this, we prove another lemma that if a block is safe, it is still safe after inserting a branch to the next
block at the beginning, which requires us to prove that the rewriter correctly computes an encoding that decodes to a
branch with the proper offset. With this lemma, we can prove the safety of all blocks changed for non-control-flow reasons.

\heading{Direct control flow.}
Instructions that perform direct control flow must be modified to account for
the additional instructions we insert. We prove that our rewriter computes and uses the correct new offset when the destination
is permitted by the policy or replaces the instruction with a branch to the abort handler, and that both cases are safe.

\heading{Unsupported instructions.}
Instructions that we do not support,
such as those that always change the instruction mode or \unpredictable{} instructions,
are replaced with a branch to the abort handler, which we prove safe similarly to the previous case.

\heading{Indirect control flow.}
The code to lookup a destination from an instruction's hash table is the same for all indirect control flow instructions,
parameterized by the register containing the destination, the bits extracted by the hash function, and the address of the table.
We prove a lemma about this code that after executing this portion of the block,
the register contains some value from the table,
and a separate lemma that the table provided consists entirely of permitted destination addresses for the instruction in question.
Proving the safety of indirect control flow blocks simply involves
(1) skipping over all of the instructions up to the table lookup,
since they are all either safe or a conditional branch to the next block
(2) applying the lemma about the table lookup code to skip to a state afterwards where we have
loaded from the table
(3) executing the rest of the block and reaching a state where we have transfered control
to the address from the table
(4) applying the lemma about the addresses in the table and concluding that we have
successfully reached another invariant point, since we are in a state in the same instruction mode and endianness
either at the start of a block for a permitted destination or the abort handler.

These cases cover every possible block generated by our CFI implementation, so a block is always safe.
Thus, we conclude that for all programs produced by the rewriter,
any trace beginning at the start of a block will only take steps permitted by the policy as long as it remains in the new text segment,
meaning our implementation is sound.
