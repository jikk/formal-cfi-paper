\section{ARMv7 Instruction Categories}
\ixb{The story here can be ``look at all these instructions whose \emph{operands} change how they need to be treated. Imagine how complex the implementation is. Imagine \emph{not} having a proof for its soundness!}

Here we categorize ARMv7 user-mode instructions based on their control-flow effects as described in \autoref{sec:cfi_design}.
There are a considerable number of instructions that can perform indirect control flow, mainly from the use of PC as an operand being permitted for data processing instructions.
We instrument most of them in the same way using the following template,
where \texttt{reg} is an arbitrary scratch register:

\begin{lstlisting}[language=c, morekeywords={STR,MOVW,MOVT,BIC,LDR,reg,sp,pc}, linewidth=\linewidth,label={lst:armv7},xleftmargin=.3cm]
STR reg, [sp, #-4]  // save the scratch register to the stack
MOVW reg, #a[16:0]  // load the original address to reg
MOVT reg, #a[32:16] // (in case pc was also used for computation)
<sanitized inst>   // run the original inst with pc replaced with reg
<table lookup code using reg>
BIC sp, sp, #0b11    // clear lower bits to word-align sp
STR reg, [sp, #-8]   // save table value to stack
LDR reg, [sp, #-4]   // restore original value of scratch register
LDR pc, [sp, #-8]    // branch to table value
\end{lstlisting}

We prove that any \Block of this form is safe as long as the sanitized instruction does not perform control flow or violate any invariants,
allowing us to prove most indirect control flow \Blocks by just applying this lemma.
To improve efficiency, a more optimal rewriter can omit loading the original address into the scratch register when the original instruction does not use the program counter as part of the computation 
or the shuffling of values from the stack if it determines that the scratch register does not need to be preserved.

\section{Hash Function Replacement}

This appendix outlines the work needed to replace the hash function with one that decreases the space overhead seen in \autoref{fig:spec2017_size} without compromising the soundness of the rewriter.
In \autoref{sec:fm_friendly} we list FM friendly design principles.
Another design principle that helps in this case is making the desired soundness/correctness properties independent of deep properties of the implementation.
For instance, the soundness of the rewriter does not depend on the cryptographic security or collision avoidance of the hash function.
