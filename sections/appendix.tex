\section{ARMv7 Instruction Categories}\label{sec:armv7_categories}
\ixb{The story here can be ``look at all these instructions whose \emph{operands} change how they need to be treated. Imagine how complex the implementation is. Imagine \emph{not} having a proof for its soundness!}

In Table \ref{tab:categories} we categorize ARMv7 user-mode instructions based on their control-flow effects as described in \autoref{sec:cfi_design}.
There are a considerable number of instructions that can perform indirect control flow, mainly from the use of \PC as an operand for data processing instructions.
We instrument most of them in the same way using the following template,
where \texttt{reg} is a scratch register:

\begin{lstlisting}[language=c, morekeywords={STR,MOVW,MOVT,BIC,LDR,reg,sp,pc}, linewidth=\linewidth,label={lst:armv7},xleftmargin=.3cm]
STR reg, [sp, #-4]  // save the scratch register to the stack
MOVW reg, #a[16:0]  // load the original address to reg
MOVT reg, #a[32:16] // (in case pc was also used for computation)
<sanitized inst>   // run the original inst with pc replaced with reg
<table lookup code using reg>
BIC sp, sp, #0b11    // clear lower bits to word-align sp
STR reg, [sp, #-8]   // save table value to stack
LDR reg, [sp, #-4]   // restore original value of scratch register
LDR pc, [sp, #-8]    // branch to table value
\end{lstlisting}

We prove that any \Block of this form is safe as long as the sanitized instruction does not transfer control or violate the invariants in \autoref{sec:formalization},
allowing us to prove most indirect control flow \Blocks by applying this lemma.

To improve efficiency, a more optimized rewriter can omit loading the original address into the scratch register when the original instruction does not use the \PC as part of the computation, 
or shuffling values from the stack if it determines that the scratch register need not be preserved, at the cost of a larger proof.
A similar \Block template that also stores the stack pointer in a scratch register is used for instructions that modify the SP,
such as load instructions that write back to the SP.

\section{Hash Function Replacement}\label{sec:hash_function}

This appendix outlines a methodology for replacing the hash function with one that reduces the space overhead in \autoref{fig:spec2017_size} without compromising rewriter soundness.
Section~\ref{sec:fm_friendly} lists \FM friendly design principles, including reducing complexity of conditional expressions, and localizing soundness invariants away from global code properties.
Our current rewriter obeys these principles by avoiding dependence on the cryptographic security or collision avoidance of the hash function.

Updating the implementation with a more space-efficient hash function entails
updating the soundness proof for the rewriter function that produces table lookup code,
and updating the soundness proof for the rewriter function that generates the policy table $T_D$ for a given destination set $D$.
It suffices to prove that after executing the instructions for computing the new hash function,
the hashed register contains a value less than the length of the table, and that the policy tables only contain permitted destinations.
