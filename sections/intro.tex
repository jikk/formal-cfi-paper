\section{Introduction}
\label{sec:intro}

% \cfi is the king of modern security defense.
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
Binary \cfi is well-established as a principled defense against control-hijacking attacks, enjoying widespread deployment with near-native overhead~\cite{bincfi, ccfir, kbouncer, ropecker,cfi2005ccs}.
However, the community has largely focused on design-level guarantees, runtime overhead, and policy generation, offering relatively weak assurance of full implementation correctness~\cite{li2020ccs}. A more fundamental approach to \cfi implementation---formal soundness, safety, and security verification of a full \emph{binary-to-binary} \cfi code rewriter---has remained beyond reach.

This gap underscores a broader challenge in security engineering: translating sound designs into correct, deployable systems is difficult and costly. Even rigorously designed systems often contain subtle flaws that emerge only after deployment~\cite{heartbleed, shellshock}. In security-critical settings, these flaws do more than degrade functionality; they undermine the trusted computing base, create false confidence, and expose exploitable weaknesses~\cite{solarwinds}.

To mitigate these risks, the community relies primarily on dynamic testing techniques, such as fuzzing and symbolic execution~\cite{fuzzing,symbolic_execution, model_checking}. While effective for anecdotally uncovering bugs, these approaches face dangerous incompleteness limitations when applied to software with vast input spaces, such as software that rewrites arbitrary untrusted code. The limitations stem not from engineering shortcomings, but from the inherent limitation of dynamic analysis.

\FMs take a fundamentally different approach. Rather than observing executions, \FMs establish stringent, univer\-sally-quantified safety, security, and correctness guarantees by proving that an implementation satisfies formally specified properties, thereby covering all program behaviors and all program inputs within the scope of the specification. Proof assistants mechanically check the resulting proof artifacts, reducing trust to the validity of the specification and the soundness of the proof checker.

Despite these unparalleled advantages, \FMs have seen limited adoption in production systems for three primary reasons:
%
First, the guarantees \FMs deliver are only as strong as the specifications they prove, which can be difficult to write accurately and completely for complex, production-ready software.
Second, proofs bind tightly to specific implementations and verification contexts, making it difficult to scale verification across large, heterogeneous, and evolving codebases.
Third, formally verifying software designed to accommodate \emph{arbitrary} binary codes as input has remained largely out of reach because the community has lacked a mature, formally verified abstraction layer of sufficient generality to serve as a foundation for such verification.

% NOTE (@kjee): specificiation to formally verifiying \cfi can be straightforward.
\pname implements binary-only (source-agnostic) \cfi by rewriting binaries to confine all control-flow transfers to policy-specified edges. It identifies and instruments control-transfer instructions (\eg jumps, calls, and returns), checking each target against the policy at runtime and triggering a safe abort on violation.
\wc{We say that} A \cfi rewriter is \emph{sound} if all possible execution traces of every rewritten binary obey the policy.

% NOTE (@kjee): FM of binary writer itself is a difficult, unexplored, open challenge.
Binary-level \cfi, built on static binary rewriting techniques~\cite{rewriter0, rewriter1, rewriter2,reassessor2023sec}, is a well-studied and mature domain\wc{area}. Yet formally verifying the correctness of a binary \cfi implementation, let alone the broader class of binary rewriters, remains an open challenge despite the long-standing availability of mature proof assistants such as Coq/\penalty0 Rocq~\cite{rocq} and Isabelle/HOL~\cite{hol}.

% NOTE (@kjee): and its core challenges lie in ...
The core difficulty is \emph{semantic generality}: rewriter soundness must hold for all possible input binaries, whether compiled, hand-written, or otherwise, not merely those drawn from a particular toolchain or compiler-sanctioned subset of the \isa\@.
%
Prior work has been largely confined to verifying concrete, fixed binaries, falling short of this bar. RockSalt~\cite{rocksalt}, for instance, successfully verifies outputs from a specific \sfi algorithm on a per-case basis, but does not verify that any \sfi rewriter always produces verifiably safe code, or that the full verifier implementation correctly implements all details of the design-level verification algorithm.
%
These implementation assurances are left to software quality control processes (\eg dynamic testing) that cannot comprehensively cover the input space of all possible binaries.

  Formal verification directly targets this challenge by reasoning over all possible inputs rather than sampled executions, enabling universal correctness guarantees that dynamic testing cannot provide. These guarantees hold regardless of binary provenance, compiler, or \isa quirk, making formal methods particularly well suited to establishing that a \cfi implementation soundly enforces its policy across the full space of binaries it may encounter.

We address this key semantic generality obstacle by building on the \Picinae{} framework~\cite{hamlen19feast,averill26bar}, which supports machine-checked proofs in which all or part of the target binary code can be a symbolic (or non-concrete) proof variable rather than a concrete program. This enables \pname to achieve verification that generalizes across arbitrary binaries, a capability no prior binary \cfi rewriter has demonstrated.

Building on \Picinae's \isa{} abstractions, \pname accurately models the architecture-specific features of ARMv7, including conditional instruction prefixes, undefined and non-deterministic effects, memory access permissions, hardware exceptions, and indirect calls and returns. This faithful modeling enables \pname to serve as the first formally verified \cfi implementation for a widely deployed architecture.

Our work explores an uncharted design space to close the assurance gap in widely deployed \cfi systems.
In summary, we offer the following contributions:

\begin{itemize}[topsep=0pt,itemsep=-1ex,partopsep=1ex,parsep=1ex, leftmargin=*]
  \item  We present \pname, a machine-checked binary \cfi framework with formalized and verified safety and security. We implement it as the first machine-checked \cfi rewriter for ARMv7 and achieve near-native overhead (\avgoh\% average on SPEC 2017).

  \item \pname analyzes arbitrary ARMv7 binaries, overcoming prior \FM limitations that require concrete inputs and enabling verification over unbounded binary spaces.
  % \pname analyzes arbitrary binaries, overcoming prior \FM limitations that require concrete inputs and enabling verification over unbounded binary spaces.

  \item  We bridge \FM and binary-level security, deriving principled \FM-aware design guidelines and uncovering subtle but critical flaws that dynamic testing alone would have missed (\autoref{sec:fm_friendly} and \autoref{sec:case_studies})
\end{itemize}

Looking ahead, this demonstrates how \isa-level abstractions enable the formal verification of security-sensitive binary rewriting tasks beyond CFI. We release the \pname codebase\footnote{\label{note0}\url{https://anonymous.4open.science/r/armcfi2026ccs}} and discuss key challenges for scaling this approach to broader classes of systems.
