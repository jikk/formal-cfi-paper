\section{Introduction}
\label{sec:intro}

% \cfi is the king of modern security defense.
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
Binary \cfi is well-established as a principled defense against control-hijacking attacks, achieving widespread deployment with near-native overhead. However, the community has largely focused on design-level guarantees, runtime overhead, and policy generation, offering relatively weak assurance of full implementation correctness (\eg via dynamic testing)~\cite{bincfi, ccfir, kbouncer, ropecker}. A more fundamental approach to \cfi implementation --- formal soundness, safety, and security verification of a full \emph{binary-to-binary} \cfi code rewriter --- has remained beyond reach.
%\kwh{[KWH] We need to be careful here to identify the overlooked problem as developing guaranteed-correct \cfi implementations, not merely the problem of finding bugs in deployed \cfi implementations.  The latter is extensively studied in the literature; the former is not.}\kjee{@KWH; tried to address; would you have a look?}

This gap underscores a broader challenge in security engineering: translating sound designs into correct, deployable systems is difficult and costly. Even rigorously designed systems often contain subtle flaws that emerge only after deployment~\cite{heartbleed, shellshock}. In security-critical settings, these flaws do more than degrade functionality; they undermine the trusted computing base, create false confidence, and expose exploitable weaknesses~\cite{solarwinds}.

To mitigate these risks, the community relies primarily on dynamic testing techniques, such as fuzzing and symbolic execution~\cite{fuzzing,symbolic_execution, model_checking}. While effective for anecdotally uncovering bugs, these approaches face dangerous incompleteness limitations when applied to software with vast input spaces, such as software that rewrites arbitrary untrusted code. The limitations stem not from engineering shortcomings, but from the inherent limitation of dynamic analysis.

\FMs take a fundamentally different approach. Rather than observing executions, \FMs establish stringent, univer\-sally-quantified safety, security, and correctness guarantees by proving that an implementation satisfies formally specified properties, thereby covering all program behaviors and all program inputs within the scope of the specification. Proof assistants mechanically check the resulting proof artifacts, reducing trust to the validity of the specification and the soundness of the proof checker.
%\ixb{I think ``validity of the specification'' rather than ``correctness'' is more accurate here. Iiuc, validity is whether the specification actually states the property the author intends.}

Despite these unparalleled advantages, \FMs have seen limited adoption in production systems for at least three reasons:
\optional{% NOTE (kjee): the following is in a way known; conventional perception... However, let's not think about/mention it here at least.
  Formal verification requires substantial effort and specialized expertise to construct proof artifacts, often rivaling or exceeding the cost of the implementation itself. Moreover, these proofs are tightly coupled to the verified code: even minor changes --- such as bug fixes, optimizations, or refactoring --- can invalidate existing proofs and trigger significant re-verification effort. This tight coupling makes it costly to maintain proofs alongside evolving codebases and limits scalability to large or heterogeneous systems.
}
First, the guarantees \FMs deliver are only as strong as the specifications they prove, which can be difficult to write accurately and completely for complex, production-ready software.
Second, proofs bind tightly to specific implementations and verification contexts, making it difficult to scale verification across large, heterogeneous, and evolving codebases.
Third, formally verifying software designed to accommodate \emph{arbitrary} binary codes as input has remained largely out of reach because the community has lacked a mature, formally verified abstraction layer of sufficient generality to serve as a foundation for such verification.

\pname implements source-agnostic (binary-only) \kjee{binary-only (source-agnostic)} \cfi by rewriting binaries to confine all control-flow transfers to policy-specified edges. It identifies and instruments control-transfer instructions (\eg jumps, calls, and returns), checking each target against the policy at runtime and triggering a safe abort on violation.
  A \cfi rewriter is \emph{sound} if all possible execution traces of every rewritten binary obey the policy.

% NOTE (@kjee): FM of binary writer itself is a difficult, unexplored, open challenge.
Binary-level \cfi, built on static binary rewriting techniques~\cite{rewriter0, rewriter1, rewriter2}, is a well-studied and mature area. Yet formally verifying the correctness of a binary \cfi implementation, let alone the broader class of binary rewriters, remains an open challenge despite the long-standing availability of mature proof assistants such as Coq/Rocq\cite{rocq} and Isabelle/HOL~\cite{hol}.

The core difficulty is semantic generality: rewriter soundness must hold for all possible input binaries, whether compiled, hand-written, or otherwise, not merely those drawn from a particular toolchain or restricted to a compiler-sanctioned\wc{compiler-respected, compiler-preserved, allowed by compilers} subset of the ISA\@.
Prior work has been largely confined to verifying concrete, fixed binaries, falling short of this bar. RockSalt~\cite{rocksalt}, for instance, successfully verifies outputs from a specific \sfi algorithm on a per-case basis, but does not verify that any \sfi implementation always produces verifiably safe executable code, or that the full verifier implementation correctly implements all details of the design-level verification algorithm.
These implementation assurances are left to software quality control processes (\eg dynamic testing) that cannot comprehensively cover the input space of all possible binaries.

\optional{%
  Formal verification directly targets this challenge by reasoning over all possible inputs rather than sampled executions, enabling universal correctness guarantees that dynamic testing cannot provide. These guarantees hold regardless of binary provenance, compiler, or ISA quirk, making formal methods particularly well suited to establishing that a \cfi implementation soundly enforces its policy across the full space of binaries it may encounter.
}

We address this key semantic generality obstacle by building on the \Picinae{} framework~\cite{hamlen19feast,averill26bar}, which supports machine-checked proofs in which all or part of the target binary code can be a symbolic proof variable rather than a concrete program. This enables \pname to achieve verification that generalizes across arbitrary binaries, a capability no prior binary \cfi rewriter has demonstrated.

This faithful modeling enables \pname to serve as the first formally verified \cfi implementation for a widely deployed architecture.

No prior work has explored this space, despite its direct relevance to closing the assurance gap in widely deployed \cfi systems. As a result, this work makes the following contributions:

  \item Built on \Picinae, \pname analyzes arbitrary binaries, overcoming prior \FM limitations that require concrete inputs and enabling verification over unbounded binary spaces.

  \item  We explore a previously uncharted intersection between \FM and binary-level security, deriving principled \FM-aware design guidelines and uncovering subtle but critical flaws that dynamic testing alone would have missed (\autoref{sec:fm_friendly} and \autoref{sec:case_studies})

Looking ahead, by building a binary rewriter framework on top of the ISA abstraction layer provided by \Picinae, this work takes a concrete step toward a broader and largely unexplored research direction: the formal verification of large families of security-sensitive binary rewriting tasks beyond \cfi.

In addition to fully releasing the \pname codebase\footnote{\label{note0}\url{https://todos}} for the community benefit, we identify the key challenges and open problems that must be addressed to realize this vision, laying the groundwork for future research in this space.
