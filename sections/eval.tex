\section{Evaluation}\label{sec:eval}

While this work focuses on the formal verification of a binary CFI rewriter’s soundness, we also evaluate \pname’s performance and soundness. We measure runtime overhead and code size growth, and assess security using representative proof-of-concept control-hijacking attacks and operational stability with real-world software.
%
Unless stated otherwise, experiments run on a Raspberry Pi 5 Model B (rev. 1.1) with a Broadcom BCM2712 quad-core Arm Cortex-A76 @ 2.4 GHz and 16 GB memory, running PiOS (Debian 12 Bookworm).
For the ARMv8 rewriter, we additionally use an Apple M3 Max, running Debian 13 as a VMware guest on a MacBook Pro.

We then present case studies demonstrating how formal verification uncovers subtle implementation bugs and architectural irregularities.

\subsection{Runtime Overheads}

\autoref{tab:spec2017}  evaluates \pname's runtime performance on rewritten SPEC CPU 2017 benchmarks. To measure overhead, we adopt a permissive policy that allows each instruction to transfer control to any other instruction in the code section. \pname incurs an average overhead of 19\%, which is comparable to prior ARM-based CFI rewriters~\cite{walls_et_al}, although some benchmarks exhibit higher slowdowns.

In particular, \cd{500.perlbench\_r} runs an interpreter-style workload with a high density of indirect control transfers, such as switch-based dispatch and function pointer invocations. Benchmark \cd{541.leela\_r} is a Go engine based on Monte Carlo Tree Search (MCTS). It exhibits highly irregular, data-dependent control flow and frequent function calls due to its recursive search structure. In both cases, the dynamic frequency of control-flow events is high, which amplifies the cost of CFI instrumentation.
%
These effects are exacerbated by architectural characteristics of ARMv7, including pervasive conditional execution and PC-relative addressing semantics, both of which complicate efficient instrumentation and increase the cost of enforcing control-flow checks.

\pname’s runtime overhead can be further reduced by leveraging emerging hardware support. These features can be integrated with minimal changes to the existing software-only, binary-to-binary rewriter, while requiring only modest extensions to the formal verification effort.

With the final rewriter, \pname incurs an average overhead of 26.5\% on the Raspberry Pi 5 and 19.6\% on the M3 Max (geometric means of 24.2\% and 18.7\%), in line with the ARMv7 results.
The rewritten \cd{723.llvm} could not be produced because the rewriter runs out of memory on this binary.

As on ARMv7, the overhead follows the dynamic frequency of indirect control transfers.
Across benchmarks, the rate of indirect branches ranges from 18 million per second (\cd{777.zstd}) to 890 million per second (\cd{710.omnetpp}), and on the M3 Max it is strongly correlated with the final overhead (Pearson $r = 0.92$).
Object-oriented and interpreter workloads such as \cd{710.omnetpp}, \cd{753.ns3}, \cd{735.gem5}, and \cd{714.cpython} dominate due to virtual calls and dispatch, whereas compute-bound kernels such as \cd{777.zstd} and \cd{706.stockfish} incur negligible overhead.

\heading{Call emulation and return prediction.}
To preserve the original program's return addresses, the rewriter emulates each call: it sets the link register to the original return address rather than to the rewritten one.
A naive emulation replaces \cd{bl dest} with \cd{mov lr, oldpc+4; b dest}.
Because no \cd{bl} executes, the processor's return address predictor is never populated, and every subsequent return mispredicts.
This incurs average overheads of 44.8\% on the Raspberry Pi 5 and 134.3\% on the M3 Max, whose wide, deeply speculative core is especially sensitive to mispredicted returns.
The final rewriter instead branches over a short trampoline and calls into it:
\cd{b L2; L1: mov lr, oldpc+4; b dest; L2: bl L1}.
The \cd{bl} pushes the rewritten return site onto the hardware return stack, while the trampoline still sets \cd{lr} to the original return address, so returns are predicted correctly despite the two extra branches.

This reduces the average overhead from 134.3\% to 19.6\% on the M3 Max and from 44.8\% to 26.5\% on the Raspberry Pi 5.
The narrower Cortex-A76 benefits less from restored prediction and pays more for the added instructions, which likely explains its higher final overhead.

\subsection{Code Size Growth}
\autoref{fig:spec2017_size} reports the static code size overhead of rewritten SPEC binaries.
\pname generates a rewritten ELF binary by augmenting the original with a new instrumented text segment and an additional section for the policy table.

The rewritten text segment is, on average, $1.36\times$ larger than the original due to the insertion of security guard code.
For the policy table, we further measure the fraction of entries that correspond to non-abort program targets.
%
Some benchmarks exhibit higher code size overhead due to a larger number of unfilled table entries.
This effect stems from our design choice of using a simple hash function (\eg one without control or branch operations), which favors verification simplicity over space efficiency. On average, the policy table accounts for 71.7\% of the total size increase.

Overall, the rewritten binaries grow substantially in size; however, the increase remains on the order of a few megabytes and incurs negligible runtime memory overhead.
Modifying the rewriter to use a better hash function to reduce space overhead can be achieved with minimal changes to the proof (see Appendix \ref{sec:hash_function}).

\subsection{Operational Stability}\label{sec:functionality_evaluation}
The SPEC CPU test suite includes self-tests for correct outputs,
and all rewritten programs pass all the self-tests.
We also tested the rewriter for functionality on the GNU Core Utilities suite, Lua, CPython, Vim, Git, and SQLite.
\pname does not require input binaries from a specific compiler or source language.
We tested C and C++ binaries produced from GCC and Clang,
as well as other binaries from languages like Rust and Zig,
and found all rewritten programs to function correctly.
