\section{Evaluation}\label{sec:eval}

While this work primarily focuses on the formal verification of a binary CFI rewriter, a problem with strong security and real-world significance, we also follow conventional evaluation practices assessing \pname’s performance. In particular, we measure runtime overhead and code size of the rewritten binaries. We further evaluate both security and correctness by implementing representative proof-of-concept control-hijacking attacks and by testing \pname on mature, real-world software to validate the stability and correctness of its instrumentation.

All evaluations are conducted from Raspberry Pi 5 Model B 1.1 (Broadcom BCM2712 quad-core Arm Cortex A76 processor @ 2.4GHz) with 16GB of memory (PiOS; Debian 13 Trixie distribution).

\subsection{Runtime and Space Overheads}

\heading{SPEC 2017 evaluation.}
\autoref{tab:spec2017}  evaluates the efficiency of \pname on rewritten SPEC CPU 2017 benchmarks. To measure runtime overhead, we adopt a permissive policy that allows any instruction to transfer control to any other instruction within the code section. \pname incurs an average overhead of \avgoh\%, which is comparable to prior ARM-based CFI rewriters~\cite{walls_et_al}.

In particular, \cd{500.perlbench\_r} represents an interpreter-style workload with a high density of indirect control transfers, such as switch-based dispatch and function pointer invocations. \cd{541.leela\_r}, a Go engine based on Monte Carlo Tree Search (MCTS), exhibits highly irregular, data-dependent control flow and frequent function calls due to its recursive search structure. In both cases, the dynamic frequency of control-flow events is high, which amplifies the cost of CFI instrumentation.

\heading{Code size growth.}
\autoref{fig:spec2017_size} measures the static size overhead of rewritten SPEC binaries.
Rewritten text segments are $1.36\times$ larger on average due to inserted security guard code.
For the table segment, we also measure how many entries contain non-abort program addresses.
Some benchmarks have high space overhead from unfilled entries
when a large table is needed to avert hash collisions.
In these cases, a better hash function can reduce size overhead.
The table segment on average contributes 73.5\% of the added size.

\subsection{Functionality}\label{sec:functionality_evaluation}
The SPEC CPU test suite includes self-tests for correct outputs,
and all rewritten programs pass all the self-tests.
We also tested the rewriter for functionality on the GNU Core Utilities suite, Lua, CPython, Vim, Git, and SQLite.
\pname does not require input binaries from a specific compiler or source language.
We tested C and C++ binaries produced from GCC and Clang,
as well as other binaries from languages like Rust and Zig,
and found all rewritten programs to function correctly.

\subsection{Security Evaluation}

\input{tables/basic_vul_tab}

\autoref{tab:poc-attacks} lists classes of control-flow hijacking exploits that we implemented to experimentally confirm \pname's immunity to policy violations.
\pname successfully instruments control-flow monitors for all binaries and blocks
the listed attacks at runtime.
We also instrument the programs to enforce overly permissive policies, confirming that the exploits succeed against policies that mount an inadequate defense.
These results confirm that the rewriter implementation correctly enforces the policy it receives as input.
